## Phase F follow-ups (new — surfaced during 2026-05-13 mass-close batch)

These are critical-capability gaps observed while shipping ~26 Phase F atomic
issues. Each one represents a **load-bearing primitive whose write-side now
exists but whose consumer / propagation path is still missing**. Without
closing these, the Phase F primitives ship as inert state rather than as
working policy enforcement.

| # | Blind spot | Why it matters | Resolution |
|---|---|---|---|
| F1 | **Pause-state file is written but predictions don't read it.** `mejepa pause --duration-mins <n>` persists `/mnt/d/contextgraph/state/cgreality/predictions_paused_until.json` with sync_all() + readback, but the inference compiler does not consult the file at the start of each verify cycle. Predictions continue running through a "pause" today. | The pause CLI/MCP tool gives the operator a button that does not actually stop new predictions. Operator runbook §5 references this surface. | New `TASK-PREDICT-013-pause-state-consumer`: `MeJepaCompiler::verify` (and `compile`, `predict`) reads the pause file on entry; if `now_ms < paused_until_unix_ms` it returns `Verdict::Abstain` with reason `MEJEPA_VERIFY_PAUSED_BY_OPERATOR` and a structured `paused_until_unix_ms` field. Stale / malformed JSON falls open with a warning so an operator deleting the file resumes predictions. FSV must cover: paused → abstain, expired pause → normal verdict, missing file → normal verdict, malformed JSON → warning + normal verdict. |
| F2 | **Operator-override BatchSampler upweight consumer.** `persist_operator_override()` writes a record with `sampling_weight_multiplier = 6.0` and `mejepa_operator_override_prediction` exposes the surface; as of 2026-05-13, `BatchSampler::new_with_operator_override_db` consumes `CF_MEJEPA_OPERATOR_OVERRIDES` and maps each override through the persisted `RealityPrediction.covered_chunks`. | TASK-PREDICT-012's DoD requires "override → next batch sampling weight 6× on affected chunks". The write side and sampler consumer now both exist; remaining work is ordinary production-training integration rather than inert state. | **Code/FSV shipped locally for `TASK-PREDICT-014` / #83.** `context-graph-mejepa-train::sampler` reads `CF_MEJEPA_OPERATOR_OVERRIDES` + `CF_MEJEPA_LIVE_PREDICTIONS`, suppresses operator-dismissed tasks from `CF_MEJEPA_ACTIVE_LEARNING_EVICTIONS`, applies the 6.0× persisted multiplier once per covered chunk, and emits per-batch `operator_override_sampler_applied_count_total` through `SystemCostCounters`. FSV: `/mnt/d/contextgraph/fsv/phase-f-override-sampler-fsv/override_sampler_fsv.json` covers 0 overrides → no boost; 1 override → 6.0× covered chunks; dismissed override → no boost; duplicate same override → still 6.0×, not 36×. |
| F3 | **System cost counters have no producer wiring.** `SystemCostCounters::{record_cuda_microseconds, record_agent_feedback_tokens, record_rocksdb_write}` exist as pure-Rust APIs but nothing in the daemon actually calls them, so every snapshot reports zeros. Weekly eval report ships a "cost" section that always reads zero. | TASK-OBS-013 DoD says "weekly report includes cost breakdown". Counters that always read zero hide operator-relevant resource burn. | New `TASK-OBS-017-system-cost-producer-wiring`: thread the counters through the verify path (CUDA kernel timing via `cudaEventRecord`), the agent-feedback handler (token-count attribute from the MCP request), and the heal-store / eval-store write paths. Weekly eval renderer publishes per-window deltas. FSV: drive 1k synthetic verify calls + 50 feedback events + 200 writes; weekly report shows non-zero values that match independent measurement within ±5%. |
| F4 | **Toolchain audit runs but daemon doesn't fail closed if it surfaces missing binaries.** `audit_required_toolchains` + `default_enabled_label_toolchains()` return structured diagnostics, but `MeJepaCompiler::new` / daemon startup do not invoke the audit. TASK-PREDICT-LABEL-010 spec says "missing required toolchain → daemon refuses to start". Today it does start. | The fail-closed property is the entire point of the audit. Without the daemon-side gate it's an idle helper. | New `TASK-FLYWHEEL-009-toolchain-audit-startup-gate`: at daemon boot, run `audit_required_toolchains(default_enabled_label_toolchains(), Some(PATH))` for the language set the operator opted into via `~/.config/mejepa/daemon.toml::enabled_languages`. Any miss → log structured `MEJEPA_LABEL_TOOLCHAIN_MISSING` and exit non-zero before opening RocksDB. FSV: run daemon with empty PATH → exit 1 + structured stderr. |
| F5 | **Cross-language label-transfer policy now has a runtime consumer and audit CF.** `label_can_transfer()` remains the policy; as of 2026-05-13, `apply_phase_b_labels_with_transfer_gate()` is the label-application path and writes every same-language, transfer, and reject decision to `CF_MEJEPA_LABEL_TRANSFER_DECISIONS`. | TASK-PREDICT-LABEL-011 DoD says "Python → Rust label with low similarity → not transferred". The consumer path now records that rejection at the source of truth instead of discarding the decision. | **Code/FSV shipped locally for `TASK-PREDICT-LABEL-012` / #86.** New module `label_transfer_audit` persists per `(prediction_id × label_source × source_chunk × target_chunk)` decisions, weekly surfaces render accept/reject ratios per language pair, and the FSV `/mnt/d/contextgraph/fsv/phase-f-label-transfer-gating-fsv/label_transfer_consumer_fsv.json` proves low-similarity Python→Rust rejection, high-similarity same-root-cause Python→Rust transfer at 0.5×, same-language full-weight acceptance, root-cause mismatch rejection, and reopen readback equality. |
| F6 | **Health-probe `/ready` now aggregates supervised daemon-task health.** As of 2026-05-13, the daemon writes `state/schedulers/supervised_task_health.json` for shift subscriber, self-optimization, nightly GC, and weekly eval tasks; `/ready` fails closed on missing/stale/restarting task rows. | k8s/systemd now withholds traffic when any supervised task is stale or unhealthy instead of relying only on the supervisor summary. | **Code/FSV shipped locally for `TASK-FLYWHEEL-010` / #87.** The health probe validates supervisor PID/status, restart flapping, task-health PID/schema, per-task heartbeat freshness, and task status. FSV: `/mnt/d/contextgraph/fsv/phase-f-health-probe-fsv/health_probe_fsv.json` proves stale shift-subscriber heartbeat, restarting shift subscriber, malformed/missing state, and a live daemon case where removing the shift-log dir makes `/ready` return 503 before recovery to 200. |
| F7 | **Deprecation framework has no caller integration.** `apply_deprecation(notice, response)` and the env-var escalation work, but no live MCP tool actually calls it. The framework is a complete in-isolation primitive with zero hookups. | TASK-API-004 DoD says "deprecated tool emits warning; opt-in error escalation works". Today nothing is wired so nothing emits warnings. | New `TASK-API-006-deprecation-call-site-audit`: identify each Phase A–E retired/deprecated MCP entry point (e.g., `mejepa_load_learner_state` if retired) and wrap its handler return through `apply_deprecation`. Add a static `phase_f_deprecation_call_sites.md` to docs that lists every wrapped tool with its `remove_after` date. |
| F8 | **Runbook coverage lint succeeds but doesn't check operator-actionable alerts** (only docs↔code parity). `MEJEPA_*` alerts that fire but have no `journalctl` instructions in `19 §5` pass the lint as long as the identifier exists in the runbook. | The lint guarantees no orphan documentation but doesn't guarantee operators have an actionable response for each alert. | Extend `scripts/ci/runbook_coverage.sh` (or add `runbook_actionability.sh`) to verify each §5 entry has a `**Investigate:**` + `**Resolution:**` subsection with at least one shell command. Tracked as a refinement on TASK-RUN-012. |
| F9 | **Witness chain integrity check has no automated repair beyond best-effort.** `MEJEPA_INFER_WITNESS_CHAIN_BROKEN` documents the rollback procedure but the daemon doesn't auto-quarantine the affected DB on detection — it keeps writing into a poisoned chain. | The runbook says "auto-repair has already attempted" but the auto-repair surface is `optimizer_witness_chain_repair_legacy` which requires manual invocation. | New `TASK-FLYWHEEL-011-witness-chain-auto-quarantine`: on integrity-check failure, the daemon sets a quarantine flag in `CF_MEJEPA_ACTIVE_POINTERS`, drops to read-only mode for write paths, and surfaces the structured alert. Heal scheduler attempts repair on the next tick; only writes resume after successful repair + operator approval. |
| F10 | **Soft-deleted session rows (via `mejepa session-cleanup`) aren't replicated to GC accounting.** Session cleanup deletes from `CF_MEJEPA_LIVE_PREDICTIONS` + `CF_MEJEPA_SHIFT_WATERMARK` with `set_sync(true)`, but the deletes don't update `CF_MEJEPA_GC_HISTORY` or `CF_MEJEPA_QUOTA_STATE`, so the operator-visible quota number drifts upward over time. | After many session cleanups the quota number reports more bytes than physically present. | New `TASK-RUN-013-session-cleanup-quota-reconciliation`: extend `run_session_cleanup` to write a `GcEvent::SessionCleanup` row to `CF_MEJEPA_GC_HISTORY` and decrement the slice in `CF_MEJEPA_QUOTA_STATE` by the byte size of the deleted rows. Weekly report reads back the new event class. |
| F11 | **No agent-identity verification on `mejepa_record_agent_feedback` or `mejepa_operator_override_prediction`.** Both MCP tools accept an `agent_id` / `operator_id` string with no signature, attestation, or origin check. Any agent invoking the daemon can claim any identity. | Per CLAUDE.md §3.4 agents are *untrusted* edit generators. Letting them self-identify defeats the purpose. | New `TASK-SEC-009-agent-identity-attestation`: add a per-session signed handshake (e.g., HMAC keyed by an operator-provided pre-shared key) so the MCP server can verify the claimed `agent_id` belongs to a configured agent. Unauthenticated callers can still write *anonymous* feedback but cannot claim privileged operator identity. |
| F12 | **No retention or TTL on `CF_MEJEPA_AGENT_FEEDBACK` or `CF_MEJEPA_OPERATOR_OVERRIDES`.** Both CFs grow monotonically. After N months of operation the inference DB carries the full audit history with no compaction policy. | The hygiene crate has retention policy hooks but neither CF declares one. Sustained-operation FSV will eventually OOM the read path on large CFs. | New `TASK-HYG-002-feedback-and-override-retention`: declare `RetentionPolicy::TimestampedRows { ttl_days: 365 }` for both CFs and have nightly GC compact / archive older rows to `/mnt/d/contextgraph/storage/cold/` per existing tier-down convention. |
| F13 | **Phase F observability covers `system_cost` and `ProductionTelemetry` but not the heal scheduler's own resource burn.** No metric tracks how many tickers ran, how many drift checks fired, how long each ticker took, or how often the scheduler flapped. The "self-optimization" path is invisible in production telemetry. | The Phase E scheduler is the heart of the system. The operator runbook (§5.1) references `MEJEPA_SCHEDULER_FLAPPING` but there's no time-series to investigate it against. | Add a `heal_ticker_telemetry_total` family of counters to `SystemCostCounters` and emit them through `ProductionTelemetryWindow`. Weekly eval renders a `heal_tickers_per_window` table. |
| F14 | **CI workflows reference Rust toolchain action `dtolnay/rust-toolchain@stable` but do not pin to SHA.** CLAUDE.md §19.3 requires "Pin GH Actions to SHA (not tag — tags are mutable)". Today the four new workflows use `@stable` (a moving tag) and `actions/checkout@v4` / `actions/cache@v4`. | A supply-chain attack on the tag would land in CI. The constitution explicitly forbids this. | New `TASK-TEST-012-pin-phase-f-workflow-actions-to-sha`: replace `@v4` / `@stable` with `@<sha40>` across `e2e.yml`, `chaos.yml`, `load.yml`, `soak.yml`. Document SHA pins in a `scripts/ci/pinned-action-shas.md` file with rotation cadence. |
| F15 | **No source-of-truth bridge between the pause state and the active-learning queue.** When predictions are paused, the active-learning queue still receives surprise / uncertainty events from the (paused) verify cycle if predictions partially execute before the pause check. | If F1 is shipped naively the queue still receives entries while paused; the operator sees noisy state. | Fold into TASK-PREDICT-013: when `verify` short-circuits with `MEJEPA_VERIFY_PAUSED_BY_OPERATOR`, do not enqueue active-learning entries even if the partially-computed surprise signal is non-zero. |
