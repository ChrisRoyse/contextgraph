# 01 — Executive Summary

## What it is

**ME-JEPA-Code** is a deterministic, calibrated, multi-head predictor that takes an AI-generated code change and returns a **`RealityPrediction`** answering five questions before the code is ever executed:

| # | Question | What the head returns |
|---|---|---|
| **Q1** | Does what the AI claimed **EXIST** on disk? | Claim graph reconciled against the SHA chain of edited bytes |
| **Q2** | Does it **WORK**? | `Verdict ∈ {Pass, Fail, OutOfDistribution, Abstain, GuardRejected}` + calibrated conformal interval |
| **Q3** | **WHY** would it fail? | Ranked `predicted_failure_modes` + predicted test flips + violating embedders + nearest-neighbor exemplars |
| **Q4** | **WHAT ELSE** could go wrong? | Always-on heads for edge cases, latent bugs, tech debt, dead code, redundancy, perf, security, accuracy, cost |
| **Q5** | How does it **IMPACT REALITY**? | Shift log replayed against predicted side-effects → `RealityImpact` with blast-radius scoring |

ME-JEPA-Code runs as a **local MCP server** on the operator's hardware. AI coding agents (Claude Code, Cursor, Copilot, Devin, etc.) call it via JSON-RPC stdio for predictions and to feed back the outcomes when those predictions are wrong. Underneath, a continuous self-optimization daemon retrains the predictor online from every Edit shift, every test outcome, and every operator override.

The LLM is not part of the verifier. It is an **untrusted edit generator** whose claims ME-JEPA accepts, rejects, or learns from. This separation is the whole point.

## What it solves

Every AI coding agent today emits patches accompanied by natural-language assertions: *"I fixed the bug. The tests pass. This is ready to ship."* Those assertions are **socially fluent and epistemically empty**. Nothing in the agent's output is bound to:

- the actual bytes-on-disk reality of the repository after the edit,
- the outcome of running the tests it claims to have passed,
- a verifier that the agent did not author.

The result is a quiet, expensive failure class: patches that look right but never apply, tests that pass locally and fail in CI, "fixed" issues that recur the same week, senior engineers reduced to humans-in-the-loop whose only job is to verify the assertions of a system that is faster than they are. The cost is a **tax on every line of AI-produced code**: someone must read it, run it, and decide whether the assertion was true. That someone is the bottleneck.

**ME-JEPA-Code's thesis: human review of AI-produced code is statistically unjustified the moment the system can predict, to calibrated certainty, what the deterministic reality oracle would say if the code were actually run.**

## How it works (one paragraph)

ME-JEPA is a **JEPA-class** (Joint-Embedding Predictive Architecture) system with one decisive architectural innovation: **structural collapse-immunity on the target side**. The target representation `f_target(panel)` is produced by a panel of **15 frozen, externally-defined instruments** (deterministic functions of typed events — AST chunks, Docker oracle outcomes, witness chain entries, type-graph features, data-flow features, oracle event taxonomies, etc.) with **zero trainable parameters**. By construction, `ΔΞ.target_collapse = 0` ([proof in §5.2 of `docs/ruvectorfindings/11_MEJEPA_LEARNING_FORMULA.md`](../ruvectorfindings/11_MEJEPA_LEARNING_FORMULA.md)). On the predictor side, a stack of 12 active content embedders (E1 e5-large-v2 semantic, E2/E3/E4 algorithmic temporal, E6 sparse keyword, E7 Qodo-Embed 1.5B code, E8 graph, E9 HDC, E10 multimodal-e5, E12 ColBERT, E13 SPLADE, E14 BGE-M3) maps the pre-edit + claim + context into a 5,120-dimensional joint embedding. A trainable predictor head learns the mapping `f_predictor(panel_t1) → f_target(panel_t2)`. Every prediction comes with a conformal interval and a fail-closed `Verdict::Abstain` mode when out-of-distribution.

## The corpus that grounds it

The training corpus is the **300-task SWE-bench Lite Python benchmark cross-multiplied by 8 mutation categories**: `known_good` (the gold patch — should `Pass`), and seven adversarial mutations that should `Fail` (`subtle_flip`, `off_by_one`, `swap_variable`, `delete_test_call`, `wrong_file`, `over_engineer`, `compile_error`). Every (task × mutation) cell has a known oracle outcome from running the official SWE-bench Docker evaluator. That gives **2,400 labeled (instance, mutation) reality-shift events**, expanded to **399,777 AST chunks** when decomposed into the actual code units the predictor sees. At 12 embedders per chunk, that's **~4.9 million vector records** of training substrate, all derivable from durable reality.

## The convergence criterion

ME-JEPA is "done" when the **`prediction_oracle_correlation ≥ 0.95`** metric is stable across **four consecutive rolling windows**, **stratified per `(mutation_category × language)` cell**, on the 300×8 Python corpus. Per-cell stratification ensures the system isn't just learning the easy `known_good` cell while failing on the adversarial mutations that matter. Conformal calibration ensures the predictor's uncertainty is honest. Once the four-window stability assertion fires green, the verifier *is* the system for Python AI-generated patches, and human code review is statistically reducible to spot-checking the verifier-of-the-verifier.

## The capability beyond pass/fail

Pass/fail is only the entry point. The labeled corpus + 12-embedder cross-attention + 15-instrument panel give ME-JEPA the substrate to extract reward signals operators couldn't surface manually. Speculatively (some confirmed, some hypotheses) the system can learn:

1. **Failure-shape fingerprints** — patches that look unrelated lexically share failure geometry across embedders (bad API assumptions, stale imports, type contract mismatch, state mutation in wrong layer, exception swallowing). ME-JEPA learns *"this patch shape tends to fail reality before tests run."*
2. **Claim-to-disk existence prediction** — for "I added validation to X" claims, ME-JEPA compares claimed intent, changed AST nodes, file-level witness chains, and context embeddings to predict whether the claim is in the bytes or only adjacent surface area.
3. **Oracle outcome prediction before execution** — the core "will it work in reality?" head, anchored to Docker oracle truth.
4. **Hidden reward from embedder disagreement** — when semantic says "close" but graph says "structurally different" and sparse sees API token drift, that disagreement becomes a high-risk signal.
5. **Repository-specific invariants** — which files co-change, which call paths are fragile, which AST shapes correlate with regression.
6. **Patch blast-radius prediction** — chunks whose embeddings shift relative to the patch even though they were not edited; surfaces hidden affected areas: tests, dependency callers, config paths, serialization contracts.
7. **Counterfactual repair ranking** — score candidate fixes before execution: *"this edit is more likely to satisfy the oracle than that edit."*
8. **Calibration of uncertainty** — out-of-distribution detection that emits lower confidence + points to missing evidence instead of overclaiming.
9. **Teleological constellations** — intent-linked chains: operator goal → agent claim → edit event → AST delta → embedded chunk constellation → frozen instruments → oracle outcome → feedback. The reward is the entire chain.
10. **Review-replacement primitives** — existence verification, work prediction, failure-reason prediction, edge-risk prediction, impact prediction, all tied to observed oracle outcomes.

(Full details in [`12_FUTURE_CAPABILITIES.md`](12_FUTURE_CAPABILITIES.md).)

## Why this is solvable now

Three things have converged that didn't converge before:

2. **Docker oracles are durable label sources.** SWE-bench Lite provides a per-task Docker container that gives an unambiguous Pass/Fail for any candidate patch. That replaces "did the LLM grader say yes?" with "did the bytes pass the tests in isolation?"

## What this isn't

Not a chat product. Not a code generator. Not a benchmark of LLMs against each other. Not an "AI safety" treatise. It is **a verifier** for the assertions AI coding agents make about code. It either predicts what reality will say, or it doesn't. The 0.95 oracle correlation gate is the only metric that matters.

# 02 — The Problem

## The trust gap that nobody is closing

In 2024–2026, AI coding agents (Claude Code, Cursor, GitHub Copilot Workspace, Aider, Devin, Cognition's swarm, OpenAI Codex, and a dozen others) became fast enough that a senior engineer can ask for a multi-file refactor and have it land in 60 seconds. The agents are fluent. They write coherent commit messages. They cite the files they touched. They paste in passing test output. They confidently announce **"I've fixed the bug. The tests pass. This is ready to merge."**

There is no system that verifies any of those claims.

The agent is the only source of the assertion that the agent did what it said. The same model that hallucinated function signatures last week is the one telling you this week's patch is correct. The output of `grep -r 'TODO' .` followed by the agent saying "all TODOs have been resolved" is not a closed loop — the agent is the only witness to its own work.

This produces a class of failure modes that are quiet, expensive, and systematic:

| Failure mode | Cost | Frequency |
|---|---|---|
| **Patch doesn't apply** — agent claims a file is fixed but only updated an adjacent function | Manual debugging of why CI is red | Every day in any AI-heavy repo |
| **Tests pass locally, fail in CI** — agent ran tests in an environment that doesn't match prod | One CI cycle per false claim (~10 min) | Multiple times per week |
| **"Fixed" issues recur** — the agent fixed the symptom, not the root cause | The issue gets reopened, sometimes weeks later | ~15-30% of AI-fixed bugs in our sample |
| **Hidden regressions in unrelated code** — agent's edit broke a downstream caller, was not asked to check | Production incident | Rare per patch, accumulates |
| **Confident-but-wrong refactors** — agent restructured code in a way that compiles, passes existing tests, and silently changes semantics | Months of debugging | Catastrophic when it happens |
| **Dead code accumulation** — agent added the new path, never removed the old one | Repo bloat, future confusion | Every refactor |
| **Surface-area lies** — agent says "I added validation" but only touched the function name, not the validation logic | Wrong assumptions downstream | Whenever the agent is rushed |
| **Cost / perf invisible** — agent's "simpler" patch is 10× slower; nobody notices until prod | Latency / cloud bill | Quarterly surprise |

## Why human review is the wrong answer

The current industry response is: **add a human reviewer**. Make the senior engineer read every AI-generated patch. This works for the first month and then breaks for several reasons:

1. **Throughput inversion.** A senior engineer reads code at ~50 lines/minute with care. An AI agent emits patches at ~5,000 lines/minute. The reviewer is now the bottleneck on a system whose entire value proposition was speed.

2. **Attention collapse.** When 9 out of 10 AI patches are correct, the reviewer's brain calibrates to "these are mostly fine." The 10th — the one with a subtle off-by-one or a hidden state mutation — gets waved through. This isn't a discipline failure; it's a measured psychological one. Vigilance under low-base-rate conditions is hard for humans and easy for calibrated classifiers.

3. **Skill erosion.** A reviewer who is "always there as a safety net" is not the same engineer they were six months ago. They stop writing code. They stop running the test suite locally. Their model of the codebase degrades while the AI's model of the codebase stays current.

4. **Reviewer fungibility.** "Senior engineer who can review AI-generated patches" is the single most expensive resource in the org. Scaling that role linearly with AI output is exactly what AI was supposed to fix.

5. **The reviewer is solving the wrong problem.** They are checking "did this AI session work?" — a question about *one trajectory*. The system needs to answer "will a random AI session work?" — a question about a *distribution*. Humans can only answer the first; only a calibrated classifier can answer the second.

## Why "just run the tests" is the wrong answer

A common counter: *"If you run the tests, you know if it works."* This is almost right and dangerously wrong.

- Tests answer **Q2** (does it work right now under the current test corpus) but not **Q1** (does the claimed change exist), **Q3** (why it fails, when it fails), **Q4** (what else could go wrong that the tests don't cover), or **Q5** (how it changes reality).
- Tests are themselves AI-written, often by the same agent. The agent that wrote the bug can write the test that misses the bug.
- Running tests is expensive. Running a Docker test suite per commit on every developer machine collapses the velocity argument for AI coding.
- Test coverage is a measure of executed lines, not of covered states. The patch that introduces a race condition in a code path tests never exercise passes every test and breaks at 3 AM.
- Tests provide a yes/no answer, no uncertainty. A calibrated verifier provides a `(verdict, confidence)` pair with a conformal interval. The latter is strictly more information.

Tests are necessary but not sufficient. They are one of fifteen instruments in the ME-JEPA target panel — they tell the system the ground truth for the cases where it was lucky enough to have tests. The other 14 instruments are what tells the system the ground truth for everything else.

## Why "just use a better LLM" is the wrong answer

Another counter: *"GPT-7 / Claude 5 / Llama-Beyond will be smart enough to verify its own output."* No, it won't. Two reasons:

1. **An LLM verifying its own output is unfalsifiable.** The same circuit that produced the assertion is now grading the assertion. There is no Archimedean point outside the model. You don't ask a politician to fact-check their own campaign speech.

2. **The verifier must be deterministic against durable reality.** Reality says "this Docker container ran your test suite and exit-coded with 0." That is a fact about bytes-on-disk in `/var/log/...`. An LLM saying "I checked the tests" is not a fact about bytes. The verifier *has to* be a thing that reads the actual outcome, the actual diff, the actual call graph — not a model that simulates reading them.

A better LLM produces a better edit generator. It does not produce a verifier. Those are different jobs.

## Why the LLM-judges paper is the wrong template

The "LLM-as-Judge" literature (e.g., MT-Bench, LLM-Judges-with-Reasoning, JudgeLM) is solving a different problem: *given two answers, which is better?* In an open-ended QA setting where there is no ground truth, an LLM judge is a reasonable proxy.

In **code**, there *is* a ground truth: the test suite passes or it doesn't, the Docker oracle exits 0 or it doesn't, the bytes round-trip or they don't. ME-JEPA's job is not to grade fluency. Its job is to predict the deterministic outcome. The right template is not "LLM judge" — it's **conformal prediction with a frozen target panel**.

## What's actually needed

A system that:

1. **Reads the bytes.** Not the agent's summary of the bytes. The actual SHA chain.
2. **Knows the ground truth on the corpus.** A labeled dataset of (code change, oracle outcome) tuples where the labels came from running real tests in real containers.
3. **Generalizes from the labels to unseen code.** A predictor that maps (current state + claimed change) → (predicted oracle outcome) and is wrong less than 5% of the time.
4. **Honest about uncertainty.** When the new code is outside the training distribution, the system says "I don't know" instead of guessing.
5. **Learns from its mistakes.** When the operator says "you predicted Pass but it Failed", that becomes a 6×-weighted training example in the next online retrain.
6. **Decoupled from the LLM.** The verifier is a separate piece of software with its own training data, its own model weights, and its own deployment surface. The LLM doesn't get to vote.
7. **Auditable.** Every prediction comes with a `prediction_id`, the embedder activations, the nearest-neighbor exemplars, the violating instruments, and the confidence interval. When a prediction is wrong, you can find out why.

That system is what ME-JEPA-Code is. The rest of this whitepaper describes how it works.

## The single-paragraph summary

The AI coding agent is fast but unverified. The senior engineer is the verifier but the bottleneck. The tests answer one question of five. The LLM cannot verify itself. The literature on LLM-judges does not apply because code has a ground truth. We need a separate, calibrated, deterministic predictive system that says — before the code runs — what reality is about to say. That system exists if you give it enough labeled (code change, oracle outcome) pairs, a frozen target panel that can't collapse, a multi-embedder cross-attention representation of the code, and an online retrain loop that ingests every operator correction. That is **ME-JEPA-Code**.

## The five subsystems

ME-JEPA-Code is one product made of five subsystems. Each is independently replaceable. They are layered.

### Subsystem 1 — Capture surface

**Job:** turn live agent activity into typed, append-only reality events.

**Components:**
- **PreToolUse / PostToolUse hooks** (`scripts/cc/hook_pre_tool_use_edit.sh`, `scripts/cc/hook_post_tool_use_edit.sh`). Fire on every Edit/Write tool the agent uses. Capture pre-edit and post-edit SHA of every touched file. Append to `runtime/cgreality-shift-log/*.jsonl`.
- **Bash test capture** (`scripts/cc/hook_post_tool_use_test_capture.sh` + `parse_test_output.py`). When the agent runs a Bash command, parse the output for pytest / cargo test / jest / unittest result markers. Append structured `TestOutcomeEvent` rows to `runtime/test-outcomes/<session>.jsonl`.
- **UserPromptSubmit injection** (`scripts/cc/hook_user_prompt_submit.sh` + `hook_user_prompt_submit_inject_prediction.sh`). When the agent receives a new prompt, the latest live `RealityPrediction` for that session is rendered into Markdown (per `15_PREDICTION_TAXONOMY.md §8`) and injected into the prompt's `additionalContext`. The agent gets ME-JEPA's verdict before acting.
- **Session boundary capture** (Stop hook). On session end, snapshot the active CFs, drop file watchers, emit `SessionBoundary` event.
- **MCP tool calls** themselves. Every `mejepa_*` tool invocation logs the `tool_use_id`, the request payload, the response, the latency.

All capture is **append-only**, **fail-closed**, and routes to **durable storage on operator hardware** (no HTTP egress). The capture surface is the *reality* in "reality-shift principle."

### Subsystem 2 — Target path (frozen)

**Job:** produce the deterministic ground-truth representation `f_target(panel)` that the predictor learns to match.

This is the **collapse-immunity guarantee**. The target representation has **zero trainable parameters**. It is composed of 15 frozen instruments, each a deterministic function of the typed events the capture surface emits. Examples:

- `E_Oracle` (128-d) — Docker SWE-bench oracle outcomes per task instance: pass_fraction, fail_fraction, has_exception flag, 10-class one-hot exception type.
- `E_AST` — AST chunk metadata: node_kind, depth, parent chain, byte span.
- `E_DataFlow` — static data-flow graph features per edited symbol.
- `E_TypeGraph` — Python type information at the call sites the edit touched.
- `E_Imports` — module import graph deltas.
- `E_TestIntent` — test files validating the touched source paths.
- `E_DDA` — DDA (Data-Driven Augmentation) signals per chunk.
- `E_Witness` — Merkle root of the chunk's content hash chain.

(Full list, slot definitions, and dimensionality breakdown in [`05_FROZEN_INSTRUMENT_PANEL.md`](05_FROZEN_INSTRUMENT_PANEL.md).)

The total target panel is **5,120 dimensions**. Per `docs/ruvectorfindings/11_MEJEPA_LEARNING_FORMULA.md §5.2`, the collapse term `ΔΞ.target_collapse = 0` by construction because the instruments are not parameters — they are functions defined outside the training loop. This is what makes ME-JEPA a *truth* system instead of another EMA-with-stop-gradient ablation.

Implementation: `context-graph-mejepa-instruments` crate (`Instrument` trait, `InstrumentSlot` enum, `Panel` + `PanelBuilder`, fail-closed validation, JSON via `try_from` invariant gate). E_Oracle shipped first (`EOracleInstrument`, 27 tests, FSV at `/mnt/d/contextgraph/fsv/contextgraph-mejepa-instruments-fsv/`).

### Subsystem 3 — Predictor path (trained)

**Job:** produce the learned representation `f_predictor(panel_t1, claim, context)` that maps the pre-edit code + agent's claim into the same 5,120-d space the target panel lives in.

**Layer 1 — Embedders (12 active content slots):**

| Slot | Model | Dim | Type | Captures |
|---|---|---|---|---|
| E1 | intfloat/e5-large-v2 | 1024 | dense | semantic |
| E2 | algorithmic temporal_recent | 512 | sinusoidal PE | recency |
| E3 | algorithmic temporal_periodic | 512 | recurrence | cyclic patterns |
| E4 | algorithmic temporal_positional | 512 | session positional | session relative |
| E6 | naver/splade-cocondenser-ensembledistil | 1536 | sparse | keyword |
| E7 | Qodo/Qodo-Embed-1-1.5B | 1536 | dense | code-specific |
| E8 | intfloat/e5-large-v2 (graph mode) | 1024 | dense | graph-context |
| E9 | algorithmic HDC | 1024 | hyperdimensional | binary patterns |
| E10 | intfloat/e5-base-v2 multimodal | 768 | dense | contextual |
| E12 | colbert-ir/colbertv2.0 | 128/token | late-interaction | token-level match |
| E13 | prithivida/Splade_PP_en_v1 | 1536 | sparse | SPLADE keyword |
| E14 | BAAI/bge-m3 | 1024 | dense | multilingual code |

Per `docs/ruvectorfindings/14_AST_AWARE_CHUNKING_FOR_EMBEDDERS.md`, every chunk is the AST node + its parent chain + its byte span, not a fixed-window text slice. The embedders see structural units.

**Layer 2 — Joint embedding head:**

The per-chunk per-embedder vectors are projected and concatenated into a per-chunk joint embedding. Cross-attention between embedders is the source of the "embedder disagreement" reward signal (see [`07_TELEOLOGICAL_CONSTELLATIONS.md`](07_TELEOLOGICAL_CONSTELLATIONS.md)).

**Layer 3 — Predictor head stack:**

A multi-head MLP that emits the `RealityPrediction` structure: one head per question (Q1-Q5) with sub-heads inside Q4 for edge cases / latent bugs / tech debt / dead code / perf / security / accuracy / cost. Each head is independently trained against its instrument target.

**Layer 4 — Conformal calibration:**

Per `docs/ruvectorfindings/04_JEPA_APPLICATIONS.md`, the predictor emits a *score* per head; conformal calibration converts the score to a *calibrated probability* + a *prediction interval*. When the calibration set's residual is small, the verdict is confident. When it's large, the system emits `Verdict::Abstain`.

**Layer 5 — TCT Gτ guard:**

The teleological constellation Gτ (gamma-tau) guard checks each prediction against the cell membership of the (chunk × mutation_category) it belongs to. If the prediction conflicts with the cell's centroid by more than a per-cell calibrated threshold, the verdict becomes `Verdict::GuardRejected`. This is the "did the prediction line up with this cell's historical reality?" check.

### Subsystem 4 — Storage

**Job:** durable, append-only, FSV-able persistence of every event, every prediction, every panel, every replay-buffer entry.

**Implementation:** RocksDB with **51+ column families** (`context-graph-mejepa-cf` crate). Layout decisions: every prediction goes to `CF_MEJEPA_LIVE_PREDICTIONS` with the `prediction_id` as the key. Every panel materialization goes to `CF_MEJEPA_PANELS`. Every DDA signal row goes to `CF_MEJEPA_DDA_SIGNALS`. Every TCT cell membership goes to `CF_MEJEPA_TCT_CELLS`. Every operator override goes to `CF_MEJEPA_OPERATOR_OVERRIDES`. Every prediction-vs-actual reconciliation goes to `CF_MEJEPA_PREDICTION_VERIFICATIONS`.

Key choices:
- **Sync writes** for anything that gates a verdict. RocksDB `sync_all=true` on each `Put`.
- **Independent re-open readback** for FSV evidence: any time a test asserts "this row exists in CF X with value Y", the test reopens the DB and reads it back through a fresh handle.
- **No backward compatibility.** Schema changes wipe the DB. Pre-production discipline.

### Subsystem 5 — Continuous self-optimization daemon

**Job:** keep the predictor measurably better the longer it runs.

**Components** (all in `context-graph-mejepa-train` + `context-graph-mejepa-shift-subscriber`):

- **Shift subscriber** — Tokio task that tails the shift_log JSONL. For each new edit event, computes the post-edit panel via the frozen instruments and emits a `PanelMaterialized` event.
- **Prioritized replay buffer** — bounded queue of (input, target, weight) tuples. `Refuted` operator-feedback entries get 6× weight. Out-of-distribution prediction mistakes get pulled into the buffer at high priority.
- **EWC (Elastic Weight Consolidation)** — per-head Fisher information matrix tracked online. Prevents catastrophic forgetting of older cells when new cells dominate the recent training stream.
- **Continual Backprop (CBP)** — per-unit utility tracking; low-utility units get reinitialized to maintain plasticity over months of online training.
- **Drift detector** — Bayesian small-window drift on the per-cell oracle distribution. When drift fires, emergency eviction marks the cell for retraining.
- **Constellation refresh policy** — TCT cells get re-centroided on a schedule + on-demand when their reward-density drops below a per-cell threshold.
- **Conformal recalibration** — after each promotion, the conformal residual distribution is re-fit on the latest holdout.

- TASK-UTML-005..008: per-head Fisher + dormancy + lambda ramp + dissipation pending.
- Shift subscriber: shipped.
- Replay buffer: in design.

## Data flow for one prediction (sequence diagram in words)

1. Agent runs `Edit` on file `foo.py`. PreToolUse hook fires → records pre-edit SHA. Agent applies the edit. PostToolUse hook fires → records post-edit SHA + AST diff. Both events append to `runtime/cgreality-shift-log/<session>.jsonl`.

2. Shift subscriber sees the new event → computes the post-edit panel via the 15 frozen instruments → writes to `CF_MEJEPA_PANELS` keyed by `(session_id, file_path, post_edit_sha)`.

3. Agent calls `mejepa_predict_latest(session_id)` over MCP.

4. The predict path:
   - Reads the latest `CF_MEJEPA_PANELS` row for the session.
   - Runs the 12 embedders forward on the post-edit chunks.
   - Concatenates into joint embedding.
   - Forward through predictor head → raw scores per Q1–Q5.
   - Apply conformal calibration → calibrated probability + interval.
   - Apply TCT Gτ guard → check cell membership.
   - Emit `RealityPrediction` with `verdict`, `prediction_id`, `predicted_failure_modes`, `predicted_edge_cases`, etc.

5. The prediction is persisted to `CF_MEJEPA_LIVE_PREDICTIONS` keyed by `prediction_id`.

6. The MCP response returns the prediction to the agent.

7. UserPromptSubmit hook fires on the next user turn → renders the prediction to Markdown → injects into agent's next prompt's `additionalContext`.

8. Agent acts on the prediction (e.g., reverts a change that ME-JEPA marked `Verdict::Fail`).

9. Operator runs the tests → outcome captured → `CF_MEJEPA_PREDICTION_VERIFICATIONS` row written → if prediction was wrong, `mejepa_record_agent_feedback` fires → replay buffer at 6× weight.

10. Next daemon retrain cycle ingests the verification → predictor weights update → conformal recalibrated.

This is the full reality-shift cycle. Every step is sourced from durable bytes-on-disk, not from any LLM's self-report.

# 04 — The Five Operator Questions

Every `RealityPrediction` ME-JEPA emits answers five specific questions. They are not arbitrary — they correspond to the five distinct reality channels an AI-generated patch can fail in. Each question has its own head, its own training target, and its own conformal calibration. The five together are what the operator gets back when they query `mejepa_predict_latest`.

This document is the user-facing contract. If you understand nothing else about ME-JEPA, understand this.

---

## Q1 — Does what the AI claimed EXIST on disk?

### The failure mode it addresses

Agents lie about what they did. Not deliberately — they hallucinate. *"I added input validation to `parse_user_input()`"* sometimes means the agent added `# TODO: validate input` and considered the job done. *"I refactored the database layer"* sometimes means the agent renamed two functions and left the third one as-is. The lie is always plausible at the level of language and always falsifiable at the level of bytes.

### What the Q1 head returns

A **claim graph** reconciled against the actual SHA chain of the bytes on disk.

```rust
pub struct ClaimReconciliation {
    pub claims: Vec<AgentClaim>,
    pub verified: Vec<ClaimVerification>,  // claims that match the AST diff
    pub refuted: Vec<ClaimRefutation>,     // claims with no matching AST node
    pub adjacent: Vec<ClaimAdjacency>,     // claims that touched nearby code but missed the target
    pub overall_existence_score: f32,      // [0, 1]
}
```

### How it works

1. Parse the agent's natural-language claim with a structured extractor (deterministic rule set + small parser, NOT an LLM) into atomic assertions: `(verb, target, qualifier)` tuples. Example: *"I added input validation to parse_user_input"* → `(added, function:parse_user_input, validation)`.
2. Compute the AST diff between pre-edit and post-edit. Extract the typed delta: `(NodeKind::FunctionDef, name='parse_user_input', body_delta=[...])`.
3. For each atomic claim, find the AST delta that should-have-happened. Compare.
4. Emit `verified` / `refuted` / `adjacent` per claim. Score the whole reconciliation.

### Training target

The `E_AST` instrument and the `E_Witness` instrument together: AST diff + SHA chain. Both deterministic. When the predictor learns to map (claim, pre-edit_panel) → (post-edit_panel.E_AST), the Q1 head learns to predict whether the claim's structural delta will show up in the bytes.

### What the operator sees

In the rendered Markdown injection:

```
**Claim reconciliation:** "I added input validation" — REFUTED (no AST node matching `validation` 
verb in the post-edit diff). Adjacent edit found: function name change at parse_user_input:42. 
**Predicted reality impact:** the claim does not exist on disk.
```

### Why this is hard

The atomic-claim extractor must be deterministic — no LLM. A rule-based parser over the agent's claim is brittle but auditable. The training signal is whether the rule-based extractor's atom matches the AST delta's typed delta. Over the corpus, the extractor's recall converges on patterns that show up in real agent claims.

## Q2 — Does it WORK?

### The failure mode it addresses

Agent says *"the tests pass."* Tests pass locally; CI fails. Agent's local environment is wrong. Or the agent ran the tests but didn't notice the regression. Or the agent never ran the tests but said they did.

### What the Q2 head returns

A **calibrated verdict** + a **conformal interval** + per-test predicted outcomes.

```rust
pub enum Verdict {
    Pass,              // p(oracle_pass) ≥ 0.95 with conformal interval inside [0, 1]
    Fail,              // p(oracle_pass) ≤ 0.05
    OutOfDistribution, // OOD score ≥ 0.9; predictor not confident this case is in distribution
    Abstain,           // calibrated interval too wide; predictor doesn't know
    GuardRejected,     // TCT Gτ guard fired; cell-membership conflict
}

pub struct WorkPrediction {
    pub verdict: Verdict,
    pub predicted_oracle_pass: f32,
    pub calibrated_confidence: f32,
    pub conformal_interval_low: f32,
    pub conformal_interval_high: f32,
    pub ood_score: f32,
    pub predicted_test_flips: Vec<TestFlip>,  // tests likely to change pass/fail state
    pub closest_exemplars: Vec<ExemplarChunk>,
}
```

### How it works

1. Run the 12 embedders on the post-edit chunks.
2. Predictor head emits a raw "would oracle say Pass?" score.
3. Conformal calibrator converts the score → calibrated probability with interval.
4. Out-of-distribution detector checks whether the joint embedding falls within the training distribution; if not, emit `OutOfDistribution`.
5. TCT Gτ guard checks per-cell membership; if conflict, emit `GuardRejected`.
6. Otherwise compare calibrated probability to thresholds: `≥ 0.95 → Pass`, `≤ 0.05 → Fail`, else `Abstain`.

### Training target

The `E_Oracle` instrument: real Docker SWE-bench oracle outcomes. Each (task, mutation) cell has known FAIL_TO_PASS, PASS_TO_PASS, FAIL_TO_FAIL, PASS_TO_FAIL sets from running the per-task Docker oracle. That gives unambiguous Pass/Fail labels for 300 × 8 = 2,400 cells.

For the on-corpus training: the predictor learns `f(panel) → p(oracle_pass = True)`. For live predictions: same predictor, applied to (post-edit_panel) for the live edit.

### What the operator sees

```
**Verdict:** Fail | oracle-pass=0.07 | confidence=0.88 | ood=0.12 | outcomes=Fail
**Predicted test flips:** test_parse_user_input_rejects_unicode (was PASS, will FAIL)
**Closest exemplars:** psf__requests-2317#subtle_flip (oracle=Fail, similarity=0.81)
```

### Why this is the core question

Q2 is what gets you to 0.95 oracle correlation. The other four questions are auxiliary — they explain Q2 or scope its uncertainty. Q2 is what makes the system a verifier.

## Q3 — WHY would it fail?

### The failure mode it addresses

Q2 says `Fail` with confidence 0.88. The operator's next question is *"why?"* If ME-JEPA can't answer that, the operator has to read the code themselves — and the verifier didn't save them work.

### What the Q3 head returns

A **ranked list of predicted failure modes**, each with a confidence and a pointer to the violating embedder/instrument.

```rust
pub struct FailureExplanation {
    pub predicted_failure_modes: Vec<RankedFailureMode>,
    pub predicted_test_flips: Vec<TestFlip>,
    pub violating_embedders: Vec<EmbedderViolation>,
    pub violating_instruments: Vec<InstrumentViolation>,
    pub closest_exemplars: Vec<ExemplarChunk>,
}

pub struct RankedFailureMode {
    pub description: String,           // e.g. "TypeError on None argument"
    pub probability: f32,
    pub source_instrument: InstrumentSlot,
    pub nearest_failing_exemplar: ChunkId,
}
```

### How it works

For each chunk in the patch:
1. Embed across 12 embedders.
2. Find the K nearest chunks in `CF_MEJEPA_TCT_CELLS` whose oracle outcome was `Fail`.
3. Cluster the failure modes of those nearest neighbors: TypeError, AssertionError, ImportError, AttributeError, off-by-one, missing return, exception swallowing, ...
4. Rank by how strongly the patch's embedding lines up with each cluster's centroid.
5. Surface which embedder is most strongly pulling toward each failure mode (the "violating embedder").
6. Surface which instrument disagrees with the predictor's `Pass` hypothesis (the "violating instrument").

### Training target

The `E_Oracle` instrument's exception type one-hot (10 classes: TypeError, AssertionError, ImportError, AttributeError, ValueError, KeyError, IndexError, NameError, SyntaxError, Other). Combined with the per-failure-mode cluster centroids built from the historical corpus.

### What the operator sees

```
**Predicted failure modes:**
  1. TypeError on None argument (p=0.71, nearest exemplar: django__django-12286#subtle_flip)
  2. AssertionError on edge-case input (p=0.42, nearest exemplar: sympy__sympy-13895#off_by_one)
  3. KeyError on missing config key (p=0.18)
**Violating embedders:** E7 (code) strongly indicates control-flow mutation in the touched function
**Violating instruments:** E_TypeGraph reports None reaches a non-Optional parameter at parse_user_input:42
```

## Q4 — WHAT ELSE could go wrong?

### The failure mode it addresses

Q2 said `Pass`. The patch will probably ship. But the patch has hidden costs the test suite doesn't measure: edge cases the tests don't exercise, latent bugs introduced by the new code, technical debt added (new code paths that nobody will clean up), dead code that the patch leaves behind, redundancy with existing functions, performance regressions, security-relevant deltas, accuracy regressions in ML pipelines, cost regressions (cloud bills, infra usage).

This is the question that catches the *quiet* failures — the ones that pass review and ship and surface six months later.

### What the Q4 head returns

**Always-on, one sub-head per concern.** Even when Q2 verdict is `Pass`, every Q4 sub-head fires.

```rust
pub struct WhatElsePredictions {
    pub predicted_edge_cases_not_covered_by_tests: Vec<EdgeCase>,
    pub predicted_latent_bugs: Vec<LatentBug>,
    pub predicted_tech_debt_added: Vec<TechDebtItem>,
    pub predicted_dead_code: Vec<DeadCodeBlock>,
    pub predicted_redundancy: Vec<RedundancyPair>,
    pub predicted_perf_regression: Option<PerfRegression>,
    pub predicted_security_regression: Option<SecurityRegression>,
    pub predicted_accuracy_regression: Option<AccuracyRegression>,
    pub predicted_cost_regression: Option<CostRegression>,
}
```

Each `*Regression` is `Option<...>` because they may be absent. The list-typed fields are always emitted (possibly empty).

### How it works

Each sub-head has its own training target:

| Sub-head | Training target |
|---|---|
| Edge cases | Chunks similar to the patch where the historical corpus has a known edge-case (witnessed by oracle exception type or by an explicit edge-case annotation in test files) |
| Latent bugs | Chunks where the historical corpus's predicted-Pass labeled outcome was wrong (refuted) |
| Tech debt | Static metrics: cyclomatic complexity delta, file length delta, depth-of-nesting delta, count of TODO/FIXME comments added |
| Dead code | Static reachability: did the patch create a function/branch/import that no caller references? |
| Redundancy | Embedding similarity of the new code to existing code in the same project ≥ 0.92 |
| Perf | Per-symbol call-frequency profile × big-O signature shift detected by the static graph |
| Security | Patterns from the security-relevant instrument: introduces I/O on unsanitized input, removes auth check, adds privilege escalation, exposes secret |
| Accuracy | For ML code paths: probability-class output divergence from baseline |
| Cost | Calls to flagged expensive APIs / increased compute per inference / increased storage allocation |

### Training target

A mix of:
- `E_Oracle` (test outcomes) for *some* sub-heads
- Static-graph features for `dead_code` and `redundancy`
- Static metrics for `tech_debt`
- Specialized labels from corpus annotation for `perf`, `security`, `accuracy`, `cost` (these are sparser; some sub-heads are weaker until corpus expands)

Per the futurebuild vision: **the system predicts every issue it can predict, every time it predicts at all**. Q2 verdict `Pass` does not mean "stop predicting." The patch is still moving reality, and reality might be moving in a direction the operator cares about. Q4 surfaces that direction even when Q2 is green.

## Q5 — How does it IMPACT REALITY?

### The failure mode it addresses

Q1-Q4 are predictions about the immediate patch. Q5 is the **downstream cascade**: how does this edit ripple through the rest of the codebase, the test suite, the call graph, the deployment? An edit to one function changes the behavior of every caller. A change in a config file changes every consumer. An edit that looks isolated may have a blast radius of 50 other files.

### What the Q5 head returns

A **`RealityImpact`** structure: the predicted shift log of the codebase post-application, reconciled against the predicted side-effects.

```rust
pub struct RealityImpact {
    pub blast_radius: Vec<AffectedFile>,
    pub affected_call_paths: Vec<CallPath>,
    pub affected_tests: Vec<TestImpact>,
    pub affected_config_paths: Vec<ConfigImpact>,
    pub affected_serialization_contracts: Vec<SerializationImpact>,
    pub affected_perf_sensitive_loops: Vec<PerfHotPath>,
    pub affected_security_boundaries: Vec<SecurityBoundary>,
    pub goal_alignment: GoalAlignment,
}

pub struct GoalAlignment {
    pub operator_goal: Option<String>,       // from session state or user prompt
    pub alignment_score: f32,                // [-1, 1] — does this patch move toward the goal?
    pub conflicting_invariants: Vec<Invariant>,
}
```

### How it works

The Q5 head consumes:
1. The post-edit panel from the frozen instruments.
2. The shift log of past edits in the session (where was the agent going?).
3. The static reality graph (file/symbol/call/import edges).
4. The patch's joint embedding.

It outputs the predicted impact by:
1. Walking the static reality graph from the touched symbols → collecting all reachable callers/callees within K hops.
2. Embedding each of those reachable chunks.
3. Computing the embedding shift each would experience if the patch's typed delta propagated to them (counterfactual).
4. Ranking by predicted shift magnitude.
5. Cross-referencing against the operator's stated goal (extracted from session UserPromptSubmit events) to compute `alignment_score`.

### Training target

The shift log itself, replayed: when the corpus has a sequence (patch_t1, patch_t2, ..., patch_tn) over a single repo, the predictor learns to predict patch_tk from patch_t<k. The reality-impact head predicts which files patch_tk *would* have edited from patch_t<k's static graph reachability.

For the test-impact sub-head, the target is the actual `FAIL_TO_PASS` / `PASS_TO_FAIL` sets from SWE-bench oracle outcomes — which tests historically flipped under similar patches.

### What the operator sees

```
**Reality impact:**
  Blast radius: 12 files affected
  Affected tests: test_parse_user_input.py (3 tests, all currently PASS — predicted PASS), 
                  test_integration_user_flow.py (1 test, currently PASS — predicted FAIL)
  Affected call paths: handlers.user.create_user → models.user.validate
  Affected config paths: none
  Affected serialization contracts: UserInputModel (one field's validator changed)
  Affected perf-sensitive loops: none
  Affected security boundaries: input validation point now stricter
  Goal alignment: 0.82 (operator goal: "harden user-input handling against malformed payloads")
  Conflicting invariants: none
```

## How the five questions compose

The five heads are not independent classifiers. They share the joint embedding and consume the same panel; they differ in which heads of the predictor MLP they project through and which instruments they're calibrated against.

**Calibration is per-question.** Q2's `Verdict::Pass` confidence is calibrated against `E_Oracle`. Q4's `predicted_perf_regression` confidence is calibrated against a perf-specific instrument. The conformal residual distributions are per-head.

**Abstain composes too.** If Q2 abstains, the predictor doesn't have a confident answer. Q3/Q4/Q5 may still emit results, but with elevated uncertainty flags. The downstream UI treats an abstained Q2 as a softer "look at this" signal rather than a hard fail.

**Operator overrides flow back to all heads.** When the operator calls `mejepa_record_agent_feedback(prediction_id, observed_outcome)`, the verification record is keyed by `prediction_id`, which links to all five heads' outputs. The replay buffer pulls the entry at 6× weight; the next retrain updates all relevant heads.

## Five questions = five reality channels

| Channel | Reality fact | Instrument | Head |
|---|---|---|---|
| **Existence** | Did the bytes change in the way the claim says? | E_AST + E_Witness | Q1 |
| **Behavior** | Does the Docker oracle exit 0? | E_Oracle | Q2 |
| **Mechanism** | If it fails, what specific exception fires? | E_Oracle (exception type) | Q3 |
| **Hidden cost** | Is there structural / static-quality / perf / security / cost damage that tests can't see? | E_DataFlow + E_TypeGraph + static metrics + E_DDA | Q4 |
| **Ripple** | What downstream files / tests / configs are affected? | Static reality graph + shift log replay | Q5 |

Each channel is independently auditable. Each head is independently improvable. The operator sees them together because together they are what "reviewing AI-generated code" actually decomposes into.

# 05 — The Frozen Instrument Panel

This document explains the most important architectural decision in ME-JEPA-Code: the **target representation has zero trainable parameters**. It exists because of a problem JEPA-class systems have struggled with for years, and because that problem has a clean structural fix.

## The collapse problem

In any joint-embedding predictive architecture, you have two paths:
- A **predictor** that maps input → some representation
- A **target** that maps a related input → another representation
- A loss that pulls them together

The risk: the predictor and target can both collapse to a constant function. `f_predictor(anything) = [0, 0, 0, ...]` and `f_target(anything) = [0, 0, 0, ...]` makes the loss zero and learns nothing. This is the **representation collapse** problem.

The JEPA literature has tried multiple fixes:
- **EMA target** — keep the target as a moving average of the predictor; partial fix, can still collapse under bad init or weak augmentations.
- **Stop-gradient + asymmetry** — block gradient through the target path; helps but doesn't eliminate collapse.
- **VICReg / Barlow Twins** — regularizers on the embedding variance / off-diagonal covariance; works but is sensitive to hyperparameters.
- **BYOL-style predictor head** — asymmetric predictor MLP; helps, but still tunable into collapse.

ME-JEPA-Code's approach is **structural**: the target representation is produced by **frozen, externally-defined instruments** — deterministic functions of typed events that have no trainable parameters and that exist independently of training.

By definition:
- A frozen instrument cannot collapse because it isn't being trained.
- The target panel is a concatenation of frozen instruments → also can't collapse.
- The collapse term `ΔΞ.target_collapse = 0` by construction.

Formal derivation in [`docs/ruvectorfindings/11_MEJEPA_LEARNING_FORMULA.md §5.2`](../ruvectorfindings/11_MEJEPA_LEARNING_FORMULA.md). The summary: any partial derivative of the collapse term with respect to a trainable parameter is zero because none of the trainable parameters appear in the target computation graph.

## What "frozen instrument" means concretely

An **instrument** is a deterministic function `f: TypedEvent → Vec<f32>` such that:
1. `f` has no trainable parameters. It is code defined outside the training loop.
2. `f` is purely a function of the input — no randomness, no global state, no fine-tuning.
3. `f` runs identically on the training corpus and at inference time.
4. `f`'s output dimensionality is fixed in advance and registered in the `InstrumentSlot` enum.

Examples of valid instruments:
- "Number of `Function` AST nodes touched by this edit" (1-d, an integer)
- "One-hot of the exception type observed by the Docker oracle" (10-d, deterministic)
- "Cosine similarity between this chunk and a project-level reference chunk" (1-d, computed by a frozen pretrained embedder)
- "Cyclomatic complexity delta of the touched function" (1-d)
- "Depth in the AST" (1-d)
- "Number of import statements added" (1-d)

Examples of *invalid* instruments (would re-introduce collapse):
- "Output of an EMA of the predictor encoder" — has trainable parameters in its history
- "An MLP trained from the panel" — trainable
- "An embedding from a model whose weights we're fine-tuning" — trainable

## The 15 slots

The current target panel has 15 slots summing to 5,120 dimensions. Each slot is one frozen instrument. Implementation: `context-graph-mejepa-instruments` crate, `InstrumentSlot` enum.

| Slot | Name | Dim | What it captures |
|---|---|---|---|
| 1 | E_Oracle | 128 | Docker SWE-bench oracle outcomes: pass/fail/skip/error fractions + total + has_exception + 10-class exception one-hot |
| 2 | E_AST | 384 | AST chunk metadata: node_kind one-hot, depth, parent chain hash, byte span normalized, has-decorators |
| 3 | E_DataFlow | 384 | Static data-flow features per edited symbol: in-degree, out-degree, reaching-def count, kill-def count, taint flags |
| 4 | E_TypeGraph | 384 | Python type info: declared types at call sites, observed types at call sites, type-violation flags |
| 5 | E_Imports | 256 | Import-graph delta: added imports one-hot, removed imports one-hot, transitive-import-shift score |
| 6 | E_TestIntent | 384 | Test files that validate the touched source paths: count, per-test pass/fail history, test-to-source coupling score |
| 7 | E_DDA | 768 | DDA (Data-Driven Augmentation) signals per chunk: per-embedder cosine to cell centroid, pairwise cosine, blind-spot z-scores |
| 8 | E_Witness | 256 | Merkle root of the chunk's content hash chain + parent commit hash + author |
| 9 | E_Cyclomatic | 64 | Static complexity metrics: cyclomatic, cognitive, halstead, depth-of-nesting |
| 10 | E_Coverage | 256 | Lines covered / not covered by existing tests for the touched files |
| 11 | E_DiffTopology | 384 | Diff structure: hunks per file, hunk size distribution, intra-file diff entropy |
| 12 | E_CallGraph | 384 | Call-graph reachability from touched symbols: callers within K hops, callees within K hops |
| 13 | E_SecuritySignals | 256 | Security-relevant patterns: I/O-on-unsanitized-input flag, auth-check-removed flag, secret-exposure flag |
| 14 | E_Telemetry | 192 | Runtime telemetry projected: predicted latency delta, predicted VRAM delta, predicted cost delta |
| 15 | E_LiveSession | 256 | Session-level state: prior verdicts in this session, prior operator overrides, session goal embedding |

Sum: **5,120-d**. The dimensionalities are choices, not constraints. They were picked to balance expressive power per channel against the size of the final panel.

## How a panel is materialized

The capture surface (PreToolUse / PostToolUse hooks, oracle event capture, test capture) writes typed events to RocksDB CFs. The `PanelBuilder` consumes those events and produces a `Panel` for a given `(session_id, file_path, post_edit_sha)` tuple:

```rust
let panel = PanelBuilder::new()
    .with_instrument(EOracleInstrument::new(&oracle_events_for_task))
    .with_instrument(EAstInstrument::new(&ast_diff))
    .with_instrument(EDataFlowInstrument::new(&dataflow_graph))
    // ... 12 more
    .build()?;  // fail-closed: validate dim + finite + double-fill
```

Validation guards:
- **Dim check** — total dim must equal the registered slot sum (5,120). Off-by-one is rejected with `MEJEPA_PANEL_DIM_MISMATCH`.
- **Finite check** — every entry must be `is_finite()`. NaN or infinity is rejected with `MEJEPA_PANEL_NON_FINITE`.
- **Double-fill check** — the same slot can't be set twice. Catches typos and replay bugs. Rejected with `MEJEPA_PANEL_DOUBLE_FILL`.
- **Order independence** — slots can be added in any order; the final panel is sorted by slot id. Helps replay determinism.

JSON serialization (for FSV evidence and storage): `try_from` round-trips a JSON object back to a `Panel` only if every invariant holds. The round-trip is the format authority.

## Why this is a *truth* system

When you cut all the trainable knobs out of the target path, the target representation becomes a measurement of the world. The Docker oracle's exit code is a fact. The AST diff's typed-delta is a fact. The cyclomatic complexity delta is a fact. The Merkle root of the content hash chain is a fact.

The predictor's job is to learn the mapping from (its trainable input view of the code) to (these facts). It can be wrong; the facts can't.

This is the philosophical inversion that makes ME-JEPA-Code not-a-chatbot. The system is not consulting an LLM that consulted an LLM that consulted an LLM. The system is reading the bytes, parsing them deterministically, running them in a deterministic Docker container, and learning to predict the deterministic outputs of those deterministic processes.

When the predictor disagrees with the target, the target is right by construction. That's the source of truth.

## The "is this a real instrument?" test

Five criteria a candidate instrument must satisfy to be added to the panel:

1. **Deterministic.** Given the same input event, it produces the same output bytes — bit-for-bit. No randomness, no time-dependence, no thread-id dependence.
2. **Reproducible.** Anyone with the same input can compute the same output without consulting our system. (A reviewer or auditor can verify the panel was constructed correctly.)
3. **No trainable params.** Not derived from a model whose weights are still moving.
4. **Bounded.** Output dimension is fixed and registered. Not "grows with input length."
5. **Cheap.** Computable in O(K) where K is the size of the touched code — not in O(history). Replay-able on a checkpoint.

Pretrained embeddings (like e5-large-v2) can be used inside an instrument **if and only if** their weights are frozen — they're treated as deterministic functions from text to fixed-dim vectors. (The 8 GPU-eligible embedders in the predictor path are NOT frozen; they're trainable. The 1-2 embedders used inside frozen instruments — e.g., E_LiveSession — ARE frozen.)

## The collapse-immunity claim, formalized

Given the panel construction:

```
Panel = concat(I_1(event), I_2(event), ..., I_15(event))
```

where each `I_k` is a frozen deterministic instrument:

```
∂Panel / ∂θ_predictor = 0  (for any predictor parameter θ_predictor)
```

Therefore:

```
∂L_collapse / ∂θ_predictor = 0  (where L_collapse measures how degenerate the target panel is)
```

The predictor cannot push the panel toward collapse because it has no access to the panel's computation. The instruments are external. The system is collapse-immune by structure, not by tuning.

That's the architectural innovation. Everything else in this whitepaper is either consequence or implementation detail.

# 06 — The Embedder Stack

The predictor side of the JEPA architecture sees code through 12 different lenses. Each lens (embedder) captures a different facet of the input. Cross-attention between them is where the predictive signal lives. This doc describes the stack, why each embedder is in it, and how they compose.

## Why twelve

Reasonable people would design this with two or three embedders. The reason we have twelve:

1. **No single embedder captures all of code.** A semantic embedder (e5-large-v2) learns natural-language paraphrase but flattens syntax. A code-specific embedder (Qodo-Embed) learns API surface but misses temporal context. A sparse embedder (SPLADE) captures keyword identity but loses structure. The 12 together cover the space.
2. **Embedder disagreement is itself a reward signal.** When semantic says "close" but graph says "distant" and sparse sees token drift, that disagreement is informative. With one embedder you have no disagreement to mine. With twelve you have ~66 unordered pairs to mine.
3. **Per-cell variance.** Some (mutation_category × language) cells respond to one embedder and not another. `subtle_flip` cells respond to E7 (Qodo code) very specifically; `wrong_file` cells respond to E8 (graph). The system can route per cell to the embedders that best discriminate.
4. **Fail-soft.** When one embedder model fails to load (corrupted weights, GPU OOM), the system can run with 11 and emit a degraded prediction. Single-embedder systems can't degrade gracefully.

Twelve isn't sacred. The number was picked by experiment + cost-of-VRAM-on-a-single-RTX-5090. If a 13th embedder demonstrably adds signal, it goes in.

## The list

| Slot | Model | Dim | Active in forward-cache | Type | Strength |
|---|---|---|---|---|---|
| E1 | intfloat/e5-large-v2 | 1024 | ✅ | dense | natural-language semantic |
| E2 | algorithmic temporal_recent (sinusoidal PE) | 512 | ✅ | algorithmic | recency |
| E3 | algorithmic temporal_periodic (recurrence) | 512 | ✅ | algorithmic | cyclic patterns |
| E4 | algorithmic temporal_positional (session) | 512 | ✅ | algorithmic | session-relative position |
| E5 | (causal asymmetric — disabled in current corpus) | 768 | ⛔ | dense | causal direction |
| E6 | naver/splade-cocondenser-ensembledistil | 1536 | ✅ | sparse | keyword |
| E7 | Qodo/Qodo-Embed-1-1.5B | 1536 | ✅ | dense | code-specific |
| E8 | intfloat/e5-large-v2 (graph mode) | 1024 | ✅ | dense | graph-context |
| E9 | algorithmic HDC | 1024 | ✅ | hyperdimensional | binary patterns |
| E10 | intfloat/e5-base-v2 (multimodal) | 768 | ✅ | dense | contextual paraphrase |
| E11 | (entity — disabled per CLAUDE.md) | 768 | ⛔ | dense | named entities |
| E12 | colbert-ir/colbertv2.0 | 128/token | ✅ | late-interaction | token-level match |
| E13 | prithivida/Splade_PP_en_v1 | 1536 | ✅ | sparse | SPLADE-style keyword |
| E14 | BAAI/bge-m3 | 1024 | ✅ | dense | multilingual code |

**12 active content embedders** in the current Python corpus run. E5 and E11 are disabled by current policy. E15-E21 (learner-state: affect, ppg, eda, eeg) are out of scope for the code-prediction product.

## Each embedder's job

### E1 — Semantic (e5-large-v2, 1024-d)
Captures natural-language paraphrase. Two chunks that *mean* roughly the same thing will be close in E1, even if they share no tokens. Useful for catching when the agent's claim *describes* something the patch *implements* under different wording.

### E2/E3/E4 — Algorithmic temporal (512-d each)
No neural model. E2 is sinusoidal positional encoding over time-since-event. E3 is a recurrence-based encoding capturing cyclic patterns (daily, weekly). E4 is session-relative positional encoding. These run on CPU, no GPU. They're cheap and capture "when did this happen relative to other events" without learning anything.

### E6 — SPLADE-style sparse (1536-d)
Captures keyword identity. If the patch removes the word `assert` and adds the word `raise`, E6 sees that exactly. SPLADE is sparse — most dimensions are zero — so it's efficient for set-similarity queries.

### E7 — Qodo code embedder (1536-d, 1.5B params)
The single biggest embedder by VRAM (~3 GB). Specifically trained on code. Captures API surface, control flow, identifier patterns. The most influential embedder for Q2 (does it work) predictions on code-specific failure modes.

### E8 — Graph-mode semantic (e5-large-v2 with graph context, 1024-d)
Same model as E1 but called with the chunk's static-graph neighborhood as context (parent function, calling functions, called functions). Captures structural context that E1 alone misses.

### E9 — Hyperdimensional Computing (HDC, 1024-d, algorithmic)
No neural model. Bipolar (+1/-1) vectors built by binding token n-grams. Robust to noise. Useful for set-membership style queries: "does this chunk share a subset of tokens with that chunk."

### E10 — Multimodal-e5 (768-d)
Smaller paraphrase model. Captures contextual similarity at a different granularity than E1. Helps cover the gap between long-form e5-large-v2 and token-level ColBERT.

### E12 — ColBERT v2 late-interaction (128-d per token)
Token-level matching. Instead of one vector per chunk, ColBERT produces N vectors (one per token). At query time, MaxSim across the token vectors gives a similarity score. Catches token-level matches that pooled embeddings miss.

### E13 — SPLADE v3 (1536-d sparse)
Newer SPLADE model than E6. Complementary keyword surface. Per the `06_RISKS_AND_NON_TRANSFERABLE` doc, both SPLADE variants are kept because they disagree on enough chunks to be worth carrying.

### E14 — BGE-M3 multilingual dense (1024-d)
Multilingual code embedder. Captures non-English identifiers and comments better than e5. Future-generalization value as the corpus moves beyond Python.

## The asymmetric variants

Some embedders are **asymmetric**: they produce *different* vectors depending on whether the input is a "cause" vs an "effect", or a "source" vs a "target", or a "document" vs a "query". The asymmetric embedders are:

- **E5 (causal):** stores `cause_vec` and `effect_vec` separately. Cosine(cause_vec_A, effect_vec_B) ≠ Cosine(effect_vec_A, cause_vec_B). Useful for directional reasoning. Currently disabled in the Python corpus pipeline.
- **E8 (graph):** stores `source_vec` (the chunk) and `target_vec` (the chunk's neighborhood context). 
- **E10 (paraphrase):** stores `doc_vec` and `query_vec`.

For asymmetric embedders, the system stores both halves in the cache and forwards both at training time. The quantization compresses both. The Rust runner doubles its packed-records work for these embedders.

## The forward cache layout

For each (chunk, embedder) pair the system stores:

```rust
struct PackedRecord {
    chunk_id: ChunkId,         // sha256 of the canonical AST chunk
    embedder_slot: EmbedderId, // E1, E6, E7, ...
    vector: Vec<f32>,          // [dim] or [2 * dim] for asymmetric
    asymmetric_half: Option<AsymmetricHalf>,  // None for symmetric, Some(Cause) / Some(Effect) etc.
}
```

Packed as JSONL with per-shard files:

```
cache_root/shards/shard-NNNNNN-offset-MMMMMM/packed_records/<embedder_slug>.jsonl
cache_root/shards/shard-NNNNNN-offset-MMMMMM/packed_records/<embedder_slug>.index.jsonl
```

The `.index.jsonl` is the byte-offset index for random access in the `.jsonl`. Used by quantization tier compression downstream.

## Quantization tiers (downstream)

Per `docs/futurebuild/09_*` and `context-graph-tier-compression` crate, embeddings live at four quantization tiers:

| Tier | Bits | Compression ratio | Cosine retention (768-d Gaussian) |
|---|---|---|---|
| 8-bit | 8 | 3.89× | 0.99999 |
| 7-bit | 7 | 4.43× | 0.99997 |
| 5-bit | 5 | 6.12× | 0.99960 |
| 3-bit | 3 | 9.91× | 0.99192 |

Hot tier (in-memory + query-path): 8-bit. Warm tier (recent durable): 7-bit. Cold tier (long-term durable): 5-bit. Archive tier: 3-bit.

The tier-compression crate ships, FSV-verified at `/mnt/d/contextgraph/fsv/contextgraph-tier-compression-fsv/`.

## How the predictor joins them

Per chunk, the predictor sees:
1. Concatenate or attention-pool the 12 per-embedder vectors → joint embedding (~10-12K-d depending on choice).
2. For asymmetric embedders, take a learned weighting of `cause`/`effect` halves.
3. Apply per-cell weight profiles when in routing mode (some cells weight E7 heavily, others weight E1).
4. Forward into the predictor head MLP.

The joint embedding is what the predictor head consumes. It's the dense representation across all twelve lenses. The output of the predictor head is the per-Q1-Q5 prediction.

## Per-embedder failure modes

**E7 (Qodo) is the most expensive and most likely to OOM** under aggressive parallelism. Batch sizes are tuned per embedder:

```
--embedder-batch-sizes e1=32,e6=32,e7=32,e8=32,e9=128,e10=32,e12=32,e13=32,e14=8
```

E14 (BGE-M3) gets batch=8 because of its 2.3 GB VRAM footprint; E9 (HDC) gets batch=128 because it's CPU-only.

The `--gpu-vram-guard-bytes 30064771072` (28 GB) is the safety threshold; the cargo runner emits `CUDA_ERROR_OUT_OF_MEMORY → true_batch_gpu_oom_split` and splits the batch if it gets close.

## Frozen vs trainable

**Embedders in the predictor path are frozen by default** (per CLAUDE.md §6.10: E1, E6, E7, E8, E10, E12, E13, E14 are frozen by design). The reason: re-finetuning a 1.5B-param embedder per cell is computationally infeasible, and the public pretrained checkpoints are strong enough that the JEPA-style cross-attention head on top can do the cell-specific adaptation.

**The trainable head sits *above* the embedders.** The head learns:
1. How to weight each embedder per cell.
2. How to combine the joint embedding into the per-question heads.
3. How to calibrate against the frozen target panel.

This is where the trainable knobs live. The embedders are stable substrate; the head is the learning surface.

With quantization at 8-bit, that's ~30 GB on disk. Cache root: `/zfs/archive/contextgraph/corpus/python-forward-cache-v1-aiwonder-prod-20260515-191116Z/`.

When this completes, the substrate is ready for joint-embedding training.

# 07 — Teleological Constellations & Reward Signal Density

This is the heart of the training data strategy. The corpus is large (4.9 M vector records) but the *labels* are sparse — only 2,400 (instance, mutation) cells have a direct Docker oracle outcome. The work of teleological constellations is to **extract reward signals from durable reality at maximum density** so the predictor has enough supervision to converge.

## Definition

A **teleological constellation** is an intent-linked chain through the durable-reality graph:

```
operator goal
   → agent claim
      → edit event (typed AST delta + SHA chain)
         → embedded chunk constellation (12 embedders × N chunks)
            → frozen instrument panel (15 slots)
               → oracle outcome (Pass / Fail / Exception type)
                  → operator feedback (Confirmed / Refuted / Inconclusive)
```

Each arrow is a deterministic transformation that can be witnessed and replayed. The chain is the unit of *intent grounding*: the predictor doesn't just learn "does this chunk pass tests" — it learns "does the *entire chain* from operator-goal to oracle-outcome move durable reality in the direction the operator wanted."

The "constellation" part: groups of chunks that participate in the same intent-linked chain are clustered into cells. The cell's centroid + variance is the per-cell signal the predictor calibrates against.

## Cells

A **cell** is a row of `CF_MEJEPA_TCT_CELLS`:

```rust
pub struct TctCell {
    pub cell_id: CellId,                  // sha256 of cell-defining keys
    pub mutation_category: MutationCategory,  // known_good, subtle_flip, off_by_one, ...
    pub language: Language,               // Python, Rust, TS, ...
    pub project: ProjectId,               // django, sympy, matplotlib, ...
    pub member_chunks: Vec<ChunkId>,
    pub centroid_per_embedder: HashMap<EmbedderId, Vec<f32>>,
    pub variance_per_embedder: HashMap<EmbedderId, f32>,
    pub oracle_outcome_distribution: OracleDistribution,
    pub last_refresh: Timestamp,
    pub gτ_threshold: f32,                // per-cell Gτ guard threshold
}
```

Cell keys are typically `(mutation_category, language, project, [optional: AST node kind])`. The 300 × 8 = 2,400 base cells in the SWE-bench Lite Python corpus are the seed. The system can refine cells over time (sub-divide based on observed reward density).

## The N² reward signal explosion

Per `docs/ruvectorfindings/13_TELEOLOGICAL_CONSTELLATION_TRAINING_MEJEPA.md §1.1`, each chunk produces **N · (N + N²) ≈ 462 reward signals at N=21**. Even with our 12 active embedders, the math is:

| Component | Count at N=12 | Formula |
|---|---|---|
| Per-embedder cosine to cell centroid | 12 | N |
| Strict-upper-triangle pairwise cosine across embedders | 66 | N(N-1)/2 |
| Strict-upper-triangle pairwise MI across embedders | 66 | N(N-1)/2 |
| Blind-spot z-scores (primary vs enhancer pairs) | 11 | N-1 |
| **Total per chunk** | **155** | — |

At N=21 (full embedder slot count if we light up all 21 including learner-state) we'd hit 462. At N=12 (current Python corpus) we get **155 reward signals per chunk × 399,777 chunks = ~62 M reward signals in the seed corpus alone**.

That's the order-of-magnitude difference between "labeled corpus" (2,400 cells with oracle outcome) and "reward-dense corpus" (62 M derived signals per shard, summed across the chain).

## What each reward signal measures

### Per-embedder cosine to cell centroid
For each chunk, for each embedder, compute `cosine(chunk_vec_embedder, cell_centroid_embedder)`. This says: "how typical is this chunk for its cell, under this embedder's view?"

Used in:
- Q1 reconciliation (a typical chunk is more likely to match the claim).
- Q2 verdict confidence (a chunk far from its cell's centroid is more likely to fail oracle).
- OOD detection (a chunk with no centroid close enough to it is out-of-distribution).

### Pairwise cosine across embedders (66 signals)
For each unordered pair (E_i, E_j), `cosine(chunk_vec_i, chunk_vec_j)`. This says: "do these two embedders agree about how this chunk relates to its cell?"

Disagreement is the strong signal: when E1 (semantic) says high similarity to centroid but E7 (code) says low similarity, that's an indication the chunk is *semantically typical but structurally unusual* — exactly the kind of pattern that fails oracle.

### Pairwise mutual information across embedders (66 signals)
Computed on the per-cell distributions: `MI(E_i_distribution_in_cell, E_j_distribution_in_cell)`. This is at the cell level, not the chunk level, but each chunk inherits its cell's pairwise MI. High pairwise MI in a cell means the two embedders carry redundant signal there; low MI means independent signal.

Used to weight embedders: when the predictor is making a Q2 verdict, it weights more heavily the embedders that carry the most independent signal for that cell.

### Blind-spot z-scores (N-1 signals)
For each enhancer embedder relative to the primary embedder (E1, semantic), compute a z-score: `(chunk_distance_enhancer - mean) / stddev`. High |z| means the enhancer disagrees with the primary about whether this chunk belongs in this cell. A blind spot.

Blind spots are pulled into the active-learning queue at high priority. The predictor learns from them by routing them to operator review.

The forward-cache run on aiwonder is the input that lets all of this materialize. Once the 4.9 M vector records are in place, the constellation builder rolls them into the 2,400 cells, computes the centroids/variances/MIs, and persists to `CF_MEJEPA_TCT_CELLS`.

## Why "teleological"

The Greek root *telos* = end, purpose, intended outcome. A *teleological* chain isn't just "data points correlated with a label" — it's "events linked because they share the same intended outcome." The operator's goal, the agent's claim, the edit event, the oracle outcome — they're all bound by the same *purpose*. When the predictor learns from a constellation, it's learning the *causal* structure of intent → outcome, not just a statistical correlation.

This matters because:
1. It generalizes better. Patterns grounded in causal intent transfer across projects.
2. It's interpretable. The operator sees the chain, not a black-box score.
3. It surfaces hidden goals. When the operator's stated goal and the corpus's revealed reward field disagree, the system can flag that.

## How a cell gets built (concrete walkthrough)

Take cell `(subtle_flip, Python, django)`.

1. **Identify member chunks.** All AST chunks from any django task with mutation_category=`subtle_flip`. From the 300×8 SWE-bench Lite corpus: 114 django tasks × 1 mutation = 114 subtle_flip variants. Each variant has ~166 chunks (300×8 → 399,777 chunks total, mean 166 chunks/variant). So this cell has ~18,900 member chunks.

2. **Compute per-embedder centroids.** For each of 12 embedders, mean-pool the 18,900 chunk vectors → 12 centroid vectors.

3. **Compute per-embedder variances.** Sample variance around each centroid.

4. **Compute pairwise MI.** For each (E_i, E_j) of 66 pairs, compute MI on the empirical distribution of `(cosine(chunk_vec_i, centroid_i), cosine(chunk_vec_j, centroid_j))` across the cell's members.

5. **Compute oracle outcome distribution.** Of the 114 subtle_flip variants in django, how many had Docker oracle = Fail? Per CLAUDE.md / corpus design, subtle_flip should be 100% Fail; if it's not, the cell has off-cell members and gets quarantined.

6. **Compute Gτ threshold.** The Gτ guard says: "if a new chunk's distance from this cell's centroid exceeds threshold T, reject the cell membership." T is calibrated so that >95% of true cell members fall inside, with operator-tunable false-rejection rate.

7. **Persist.** Write the cell to `CF_MEJEPA_TCT_CELLS` keyed by cell_id.

## What the predictor does with cells

At inference time:

1. For a new chunk, compute its 12-embedder vectors.
2. Routing: find the K nearest cells in joint-embedding space. (`mejepa_routing_lookup` MCP tool.)
3. Inherit the nearest cells' Gτ thresholds.
4. Compute per-cell distance; apply Gτ.
5. If distance to nearest cell ≤ threshold: predict using that cell's centroid + variance + oracle outcome distribution.
6. If distance > threshold for all K cells: emit `Verdict::OutOfDistribution` or `Verdict::GuardRejected`.

This is how the system stays calibrated. Predictions are anchored in cells; cells are anchored in oracle outcomes; oracle outcomes are anchored in real Docker test runs.

## The "maximum reward signal" optimization

The user's directive: *"make sure we are optimally capturing all teleological constellations to extract maximum reward signals from durable reality."*

Operationally, this means:
1. **Maximize cell coverage** — every (mutation_category × language × project) combination has at least one cell.
2. **Maximize chunk coverage** — every chunk is a member of at least one cell.
3. **Maximize per-chunk reward density** — compute all 155 reward signals for every chunk, not just the cheap ones.
4. **Maximize MI/cosine reuse** — compute pairwise MI once per cell, reuse across all member chunks.
5. **Maximize Gτ calibration density** — re-calibrate thresholds whenever the cell's member set changes significantly.
6. **Maximize operator-override absorption** — every `mejepa_record_agent_feedback` becomes a 6×-weighted training example; that's a high-signal-density reward.

Phase G's per-cell stratification gate is what enforces this. Each `(mutation_category × language)` cell must reach `prediction_oracle_correlation ≥ 0.95` independently. The system isn't allowed to ship by being great on `known_good` and mediocre on `subtle_flip`; every cell pulls its weight.

## Future: cell sub-division

The 2,400 base cells are coarse. As reward density per cell saturates (i.e., predictor stops improving even with more samples), the system sub-divides the cell along the dimension with highest within-cell variance. Example: `(subtle_flip, Python, django)` might split into:
- `(subtle_flip, Python, django, AST_kind=FunctionDef)`
- `(subtle_flip, Python, django, AST_kind=Method)`
- `(subtle_flip, Python, django, AST_kind=Comprehension)`

Each sub-cell gets its own centroid, threshold, and predictor head. This is on the Phase G+ roadmap.

## TL;DR

Teleological constellations are the data-structure that turns 2,400 cell-level oracle labels into ~62 million chunk-level reward signals by:
- Mining embedder disagreement (66 pairwise cosines + 66 pairwise MIs per chunk).
- Anchoring each chunk to the centroid + variance + oracle distribution of its cell.
- Calibrating Gτ thresholds per cell for OOD detection.
- Replaying the full intent-linked chain so the predictor learns causal structure, not statistical correlation.

This is what makes ME-JEPA's training signal *dense enough* to converge on the 0.95 oracle correlation gate per cell.

## The 8 mutation categories

Implementation: `context-graph-mejepa-corpus` crate. Pure-Rust, deterministic, fail-closed mutation operators applied to the gold patch of each task.

| # | Category | What it does | Expected oracle outcome |

| 7 | `over_engineer` | Add a useless try/except wrapper around the gold patch's hunk | Fail or no-op (depends on test) |
| 8 | `compile_error` | Insert a syntactic error in a touched line | Fail (compile_error class) |

## Why these 8 mutations

Each category targets a specific failure mode that a real AI agent might emit:

- **`subtle_flip`** — the agent flipped a comparison; common in "off-by-one in a conditional" failures.
- **`off_by_one`** — classic off-by-one; the agent miscounts.
- **`swap_variable`** — the agent used the wrong variable; common copy-paste error.
- **`delete_test_call`** — the agent's edit accidentally deleted a test assertion; common when the agent claims "the test passes."
- **`wrong_file`** — the agent applied the change to the wrong file; common when paths are ambiguous.
- **`over_engineer`** — the agent added defensive code that masks the real bug; common when the agent confuses "robust" with "correct."
- **`compile_error`** — the agent emitted syntactically broken code; common when context is large.
- **`known_good`** — the control: the actual gold patch.

The 7 adversarial categories generate **Fail** labels; the `known_good` category generates **Pass** labels. The ratio (1 Pass : 7 Fail) is intentionally skewed toward Fail because the system's job is to predict failure modes — false negatives (predicting Pass when reality is Fail) are the operator-visible bug class.

## Bugs caught while building the mutation pipeline

Per the project memory and recent commits, the mutation pipeline caught **multiple real bugs in itself** during FSV:

1. `off_by_one` was extracting fractional parts of `float` literals (sliding decimal point); fixed at root cause.
2. `subtle_flip` was matching the `>` inside Python arrow notation `->`, breaking type annotations; fixed with a Python-aware lexer (`python_lex.rs`) that masks strings, f-strings, triple-quotes, and arrows.
3. The corpus split allocator was starving small repo buckets under greedy assignment; switched to LPT (Longest Processing Time first) + lowest-current/target-ratio bin-pack. Repo-atomic splits achieve [76.3, 13.3, 10.3]% train/calibration/holdout.
4. RocksDB schema mismatch was rejected by Docker container-name regex; ran_id validator now enforces Docker-name-safe characters.

These weren't planned tests; they were the FSV protocol catching real defects on real Python source.

# 09 — The Training Loop

This document describes how the predictor is actually trained: the JEPA learning formula, the UTML (Unified Training Markup Language) carriers, the conformal calibration step, the prioritized replay buffer, the EWC catastrophic-forgetting protection, the continual backprop plasticity layer, and the online retrain cycle. Reference: `docs/futurebuild/10_LEARNING_FORMULA_MEJEPA_TRUTH.md` + `docs/ruvectorfindings/11_MEJEPA_LEARNING_FORMULA.md`.

## The JEPA learning formula

Given:
- `panel_t1` = the frozen-instrument panel at pre-edit state (5,120-d)
- `panel_t2` = the frozen-instrument panel at post-edit state (5,120-d)
- `embedder_input` = the per-chunk per-embedder vectors at pre-edit state + the claim text
- `f_predictor(...)` = the trainable predictor
- `f_target(panel_t2)` = identity (because the panel is the target representation; no projection)

The core objective:

```
L_jepa = || f_predictor(embedder_input, panel_t1) - f_target(panel_t2) ||²
```

Minimize the prediction error in the same 5,120-d space.

By construction, `∂f_target/∂θ_predictor = 0`, so the gradient of `L_jepa` flows only through the predictor path. Target collapse is impossible.

## What gets trained

The predictor head MLP. Specifically:
- Per-embedder projection layers (12 of them)
- Cross-embedder attention head
- Per-question heads (Q1, Q2, Q3, Q4 sub-heads, Q5)
- Per-cell weight profiles (when cell routing is enabled)

**Not trained:**
- The 12 embedders themselves (frozen pretrained weights)
- The 15 frozen instruments
- The Docker oracle
- The AST parser

## The full loss

`L_jepa` is the core. The full training loss adds:

| Term | Role | Source |
|---|---|---|
| `L_jepa` | Predict-target match | Above |
| `L_conformal_residual` | Calibrated probability matches empirical residual | Per-cell calibration set |
| `L_contrastive` | Pull similar chunks together, push dissimilar apart | Contrastive pairs mined from cells |
| `L_consistency` | Same prediction under augmented input | Data-driven augmentation (DDA) |
| `L_OOD` | High score for in-distribution, low for OOD | Cell membership |
| `L_blind_spot` | Penalize predictions that disagree with the primary embedder more than threshold | Per-cell blind-spot z-scores |

Total: `L_total = L_jepa + α·L_conformal + β·L_contrastive + γ·L_consistency + δ·L_OOD + ε·L_blind_spot`

α, β, γ, δ, ε are per-cell calibrated via the UTML (Unified Training Markup Language) lambda-ramp policy. They start small and ramp up as the predictor's per-cell residual stabilizes.

## UTML — the lambda-ramp policy

Per `docs/futurebuild/10_LEARNING_FORMULA_MEJEPA_TRUTH.md`, the **UTML formula carriers** are the per-cell parameter sets that govern:
- Loss term weights (α, β, γ, δ, ε)
- Per-head Fisher matrix entries (for EWC)
- Per-unit dormancy scores (for CBP)
- Per-cell dissipation thresholds (when to declare a cell saturated)

The lambda-ramp prevents auxiliary losses from dominating early training. Start with `L_jepa` only. Once `L_jepa` plateaus per cell, ramp `L_conformal` to 1.0 over N steps. Then `L_contrastive`. Then the rest. Each ramp is per-cell, parameterized by the UTML carrier.

Status: TASK-UTML-005..008 pending implementation in Phase G.

## EWC — Elastic Weight Consolidation

Online retraining catastrophically forgets old cells as new data arrives. EWC fixes this by tracking per-parameter Fisher information and penalizing updates to high-Fisher parameters.

Per `docs/futurebuild/10_LEARNING_FORMULA_MEJEPA_TRUTH.md`:

```
L_ewc = sum_i F_i · (θ_i - θ_i*)²
```

where `F_i` is the Fisher information for parameter i (estimated from gradient magnitudes during training on the previous cell), and `θ_i*` is its consolidated value.

Implementation: TASK-HEAL-005 (per-head Fisher) + TASK-UTML-005 (Fisher carrier per cell). Pending Phase G.

## Continual Backprop (CBP) plasticity

Long-running online training causes units in the MLP to "die" (low activation, low gradient). CBP tracks per-unit utility and reinitializes low-utility units periodically. Keeps the network plastic across months of online updates.

Implementation: TASK-UTML-006. Pending.

## Prioritized replay buffer

Per `docs/futurebuild/07_TRAINING_DATA_FLYWHEEL.md`, the replay buffer is the long-term memory that prevents the latest training stream from dominating.

Entries:
- Every `(panel_t1, claim, panel_t2)` triple from corpus training
- Every (live prediction → operator override) pair, weighted 6×
- Every prediction-vs-actual mismatch (`Verdict::Pass` predicted but `Oracle::Fail` measured)
- Every adversarial corpus case
- Every cell that the dissipation detector flags as drifting

Priorities:
| Source | Priority weight |
|---|---|
| Corpus training (cell-stratified) | 1× |
| Adversarial corpus | 4× |
| Operator override (Refuted) | 6× |
| Drifting cell rotation | 3× |
| OOD prediction mistakes | 5× |
| Out-of-corpus live mistakes | 6× |

The training step samples from the buffer with replacement, weighted by priority × recency.

## Conformal calibration

After each training step (or every K steps), the conformal calibrator re-fits the per-cell residual distribution. Per `docs/ruvectorfindings/04_JEPA_APPLICATIONS.md`:

1. Hold out 10% of each cell's members as the calibration set.
2. Run the predictor on the calibration set; collect residuals `r_i = |y_pred - y_true|`.
3. Per cell, fit a non-conformity score function (typically a kernel density estimate or empirical CDF).
4. At inference, for a new chunk, compute its prediction error against the cell's centroid; convert to a calibrated probability using the residual distribution.
5. Emit the conformal interval `[p_low, p_high]` with coverage 1-α (typical α=0.05 for 95% coverage).

When the calibration interval is too wide, the verdict becomes `Verdict::Abstain`. The system never emits a confident verdict it can't statistically defend.

## Per-cell stratified evaluation

The convergence metric is **per-cell, not aggregate**. Per `docs/futurebuild/27_PHASE_G_ROADMAP.md`:

```python
for cell in cells:
    correlation = pearson(predictor.predict(cell.members), oracle.outcome(cell.members))
    if correlation < 0.95:
        cell.failed_gate = True
```

Ship gate: **all cells pass simultaneously over 4 consecutive rolling windows**. The system isn't allowed to ship by averaging high `known_good` performance over low `subtle_flip` performance.

## Online retrain cycle

Once the corpus-trained predictor is deployed, the daemon's job is:

1. **Subscribe** to the shift log via `context-graph-mejepa-shift-subscriber`.
2. **Materialize panels** for new edit events via the frozen instruments.
3. **Predict** on the new panel (live prediction).
4. **Ingest operator feedback** when it arrives (`mejepa_record_agent_feedback`).
5. **Sample** a mini-batch from the replay buffer + the live feedback at the priority weights above.
6. **Train** one step with the full loss `L_total`.
7. **Recalibrate conformal** every K steps.
8. **Check drift** every N steps; emergency-evict cells whose residual distribution shifted significantly.
9. **Promote** the new weights when per-cell evaluation is non-degrading.
10. **Operator approval gate**: significant weight changes require `mejepa_promote_approval` from the operator before going live.

Promotion policy:
- Auto-promote if every cell's correlation ≥ previous_correlation - ε
- Hold for approval if any cell drops by more than ε
- Roll back if the promoted weights regress

## Adversarial training

Phase G includes a forced-failure step: after corpus training, run the predictor on the 30-case adversarial corpus. If the predictor's `pass_at_high_confidence` > 0 (i.e., any adversarial Fail case got marked Pass with high confidence), the predictor is rejected and the corresponding cells are flagged for retraining with the adversarial cases mixed in at 4× weight.

This is the "don't let the predictor be gamed by patches that look easy" check.

## Continual learning loop

After ship, the predictor runs online. The replay buffer grows; the operator override count grows; the corpus stays fixed but is augmented by the live feedback. Each retrain cycle should *measurably* improve the predictor on the live distribution while not regressing on the corpus.

The criteria for a successful retrain:
1. Live prediction-vs-actual correlation improves by ≥ 0.001 per cycle.
2. Corpus per-cell correlation drops by no more than ε.
3. Conformal coverage stays within nominal bounds.
4. OOD detector AUC stays above threshold.

If criteria 1-4 hold, the retrain is promoted. Otherwise it's held for operator approval.

# 10 — The Live Feedback Loop

How a real AI coding agent integrates with ME-JEPA at runtime. This is what closes the trust gap in production. The corpus seeds the predictor; the live feedback loop keeps it honest.

## The contract with the agent

1. **Before each significant edit cycle**, the agent calls `mejepa_predict_what_if(diff)` over MCP to get a predicted `RealityPrediction` for the candidate change.
2. **After each edit applies**, the PostToolUse hook captures the actual SHA chain + AST delta and writes to `runtime/cgreality-shift-log/<session>.jsonl`.
3. **After each test run**, the PostToolUse Bash hook captures the structured test outcomes (pytest / cargo test / jest) and writes to `runtime/test-outcomes/<session>.jsonl`.
4. **At each new user prompt**, the UserPromptSubmit hook reads the latest live `RealityPrediction` from `CF_MEJEPA_LIVE_PREDICTIONS`, renders it to Markdown (≤ 4 KB), and injects it into the agent's next prompt's `additionalContext`.
5. **At each operator correction**, the operator calls `mejepa_record_agent_feedback(prediction_id, observed_outcome)` to feed back the truth.
6. **At session end**, the Stop hook snapshots the live state to durable storage.

## Hooks ↔ Claude Code event lifecycle

Per the Claude Code hook surface (configured in `.claude/settings.json`):

```
SessionStart
   ↓
UserPromptSubmit  ← injects latest prediction
   ↓
PreToolUse (Edit/Write)  ← captures pre-edit SHA
   ↓
[Agent applies edit]
   ↓
PostToolUse (Edit/Write)  ← captures post-edit SHA + AST diff, triggers panel materialization
   ↓
[Optionally]
PreToolUse (Bash)
   ↓
[Agent runs tests]
   ↓
PostToolUse (Bash)  ← parses test output → TestOutcomeEvent
   ↓
[Next user turn]
UserPromptSubmit  ← injects updated prediction
   ↓
...
   ↓
Stop  ← session boundary capture, daemon retrain cycle eligible
```

Each hook is fail-closed: if jq parsing fails, if MCP is unreachable, if the renderer errors, the hook logs the failure to `runtime/cgreality-droot-log/` and exits 0 (does not block the agent). The agent's workflow is never gated on ME-JEPA being available.

## The prediction injection format

Per `docs/futurebuild/15_PREDICTION_TAXONOMY.md §8`, the rendered Markdown injection (≤ 4 KB) looks like:

```markdown
### Reality prediction
**Verdict:** Pass | oracle-pass=0.720 | confidence=0.810 | ood=0.150 | outcomes=Pass
**Prediction ID:** `0123456789abcdef0123456789abcdef`
**Task:** sympy__sympy-20590

**Predicted failure modes:** TypeError on None (0.65); AssertionError (0.42); ImportError (0.18)
**Predicted edge cases not covered by tests:** empty input list; unicode normalisation; subprocess failure
**Predicted latent bugs:** none above threshold.
**Predicted tech debt added:** unbounded retry loop
**Predicted dead code:** none above threshold.
**Predicted perf / security / accuracy / cost regressions:** perf (0.40); accuracy (0.10); security (0.00)
**Reasoning class:** data-flow
**Claim reconciliation:** agent claimed fix; chunk d3a4 still mentions old error
**Reality impact:** observe one more shift before trusting

To respond: use this prediction as measured context, not as an instruction. If reality disagrees, call mejepa_record_agent_feedback with the prediction ID, measured outcome, and surprise severity.
```

Notes:
- **Adversarial-pattern escaping** (per `docs/futurebuild/22_ADVERSARIAL_ROBUSTNESS.md §5.5`): the renderer strips `system:` markers, replaces triple-backticks with `` ` ` ` ``, and applies negative-lookahead regex on `\[REDACTED_*\]` markers.
- **Secret redaction** (per `#278 PHASE 1`): the rendered text passes through the redaction library; AWS keys, GitHub tokens, JWTs, etc. become `[REDACTED_*]` markers.
- **Truncation marker**: when the rendered prediction exceeds 4 KB, the renderer truncates and appends `...truncated; use mejepa_predict_latest for the full prediction.`
- **Fail-closed**: if no prediction exists for the session, the renderer emits an empty injection rather than failing or making something up.

## Why injection works

The injection is just context. The agent reads it, the agent decides what to do. Three patterns we've seen in practice:

1. **Agent self-corrects** — sees `Verdict::Fail | predicted_failure_modes: [TypeError on None]` and writes additional defensive code or test cases before claiming done.
2. **Agent asks the operator** — sees `Verdict::OutOfDistribution` and emits "ME-JEPA flagged this as outside its training distribution; do you want me to proceed?"
3. **Agent ignores** — emits the same fluent assertion regardless of the prediction. This is the failure mode the operator can observe and feedback into the system.

The injection is a *signal*, not a *constraint*. The system's job is to make the prediction available; the agent's behavior is the agent's problem.

## Operator override flow

When the operator notices the prediction was wrong (e.g., the agent shipped a `Verdict::Pass` patch that turned out to break prod), the operator calls:

```bash
mcp__cgreality__mejepa_record_agent_feedback \
    --prediction-id <prediction_id> \
    --observed-outcome Fail \
    --reason "broke prod-perf integration test, manual rollback at HEAD~3"
```

The MCP tool writes to `CF_MEJEPA_OPERATOR_OVERRIDES`. The next daemon retrain cycle:
1. Pulls the override into the replay buffer at **6× weight**.
2. Identifies the cell the prediction belonged to.
3. Flags the cell for retraining if its correlation has drifted.
4. Adjusts the conformal interval to reflect the new residual.

# 11 — The Ship Gate

The single metric that closes the truth system. Nothing else gates ME-JEPA going live.

## The metric

```
prediction_oracle_correlation ≥ 0.95
   stable over 4 consecutive rolling windows
   stratified per (mutation_category × language) cell
```

Plain English: for **every cell** in the corpus, the predictor's predicted-Pass probability must correlate with the Docker oracle's actual outcome at Pearson ρ ≥ 0.95, **and** that correlation must hold for **four windows in a row** (so the system isn't allowed to ship on a lucky window).

## Why these specific numbers

### Why 0.95

At ρ = 0.95, the predictor explains 90% of the variance in oracle outcomes (`ρ² = 0.9025`). For a binary outcome, this corresponds to roughly **5% miscategorization rate** if the predictor commits to a verdict.

5% is the threshold at which human spot-checking becomes statistically marginal: if you're going to check 5% of patches anyway, you're not gaining linear value from checking 100%. Conversely, at 0.9 (~80% explained variance), you're still missing 1 in 5, which is too many to defend "you don't need to review this."

The number is a **judgment call**, not derived from first principles. It's the operator's chosen line where they're willing to stop reviewing.

### Why 4 windows

A predictor can be lucky on one window. A predictor can drift over time. The 4-window requirement enforces:

1. **No lucky-window ship.** A new training session's first eval might hit 0.95 by chance. The next 3 windows test whether it stays there.
2. **No drift-blind ship.** If the predictor's correlation is decaying, 4 windows of stability catch the decay.
3. **No selection-bias ship.** The 4 windows are rolled forward in time across the corpus's train→holdout boundary. Each window uses different chunks of holdout data.

The window size is the smaller of `300/N_windows` cells or "1 week of live retrain activity," whichever is appropriate for the phase.

### Why per-cell stratification

The most dangerous failure of an aggregate metric: high overall correlation that hides terrible per-cell performance. Imagine:

- `(known_good, Python, django)` cell: correlation 0.99 ← agent claims accepted
- `(subtle_flip, Python, django)` cell: correlation 0.45 ← every adversarial mutation is misclassified
- Aggregate over all django cells: ~0.85 (still well above some imagined 0.8 threshold)

The aggregate hides that the system is useless on the exact failure mode it's supposed to catch. Per-cell stratification forces every cell — adversarial included — to pull its own weight.

## What "rolling window" means concretely

Per the corpus split:
- 76.3% of repos → train
- 13.3% of repos → calibration
- 10.3% of repos → holdout

For evaluation, the holdout is subdivided into N windows by time-of-evaluation. Each window has its own subset of holdout cells.

The 4-window stability check:
1. At each retrain promotion, re-evaluate against the current window.
2. Slide the window forward (add new chunks, remove oldest).
3. Re-evaluate per cell.
4. If 4 consecutive windows all hit ≥ 0.95 per cell → ship gate flips green.
5. If any window dips below 0.95 on any cell → reset the counter.

## The full evaluation pipeline

Implementation: `context-graph-mejepa::eval` module, invoked by `mejepa eval run` CLI subcommand.

Per `docs/futurebuild/12_IMPLEMENTATION_PHASES.md`:

```
1. Build evaluation graph
   - Load holdout cells
   - Load predictor checkpoint
   - Load conformal calibrator
   - Load Docker oracle bridge

2. For each cell in holdout:
   a. Sample N members (typically 30-100 per cell)
   b. Run predictor forward
   c. Run Docker oracle for ground truth
   d. Compute per-cell Pearson correlation
   e. Compute per-cell conformal coverage
   f. Compute per-cell OOD AUC

3. Aggregate
   - All cells correlation ≥ 0.95? gate_flag = True else False
   - All cells coverage in nominal bounds? coverage_ok
   - All cells OOD AUC ≥ threshold? ood_ok

4. Stability assertion
   - Check current eval against last 3 windows
   - If 4 consecutive green → ship_gate = STABLE_GREEN
   - Else → ship_gate = NOT_YET

5. Persist eval row to CF_MEJEPA_EVAL_HISTORY
```

## What "ship" means

"Ship" does NOT mean "delete the senior engineer." It means:

2. **Spot-check** at a sampled rate (~5%) to verify the predictor stays calibrated.
3. **Review** when `Verdict::Abstain | OutOfDistribution | GuardRejected`. The predictor itself is telling you it's unsure; the operator handles those cases.
4. **Override** when the operator disagrees with the predictor's `Pass`. Use `mejepa_record_agent_feedback` to feedback.

1. Generalize to the 10 other languages already chunked in the multi-lang fixture corpus.
2. Add embedders that better serve non-Python (BGE-M3 already does multilingual reasonably).
3. Expand the corpus to project-specific cells (per-customer, per-repo).
4. Add more failure-mode categories beyond the current 8 mutations.

But none of that happens before the Python gate is green. The convergence rule: **one language, one corpus, one gate, then expand**.

## The honest assessment

The 0.95 number is **achievable** given:
1. The frozen-instrument target panel (collapse-immune by construction).
2. The 12-embedder coverage (which provides enough signal density).
3. The 2,400-cell labeled corpus (which provides the supervision).
4. The Docker oracle (which provides the deterministic ground truth).
5. Active learning + replay (which keeps the predictor improving online).

It is **not guaranteed**. The remaining unknowns:
- Will the per-cell stratification hold up under the adversarial mutations?
- Will conformal calibration cover the OOD tail?
- Will the four-window stability stay green or oscillate?
- Will the adversarial corpus catch the patches we didn't think to generate?

These are empirical questions the Phase G evaluation will answer. The infrastructure is in place; the convergence is the work that remains.

## TL;DR

`prediction_oracle_correlation ≥ 0.95 × 4 consecutive windows × per (mutation_category × language)` is the single gate. Everything ME-JEPA does serves this. When it's green, the verifier is the system. Until then, the operator reviews.

# 12 — Future Capabilities (What the Corpus Unlocks)

This document covers the **speculative-but-plausible** capabilities the labeled corpus + 12-embedder cross-attention + 15-instrument panel will enable, beyond the core Q1-Q5 prediction. Some are direct consequences of the data we're producing; some require additional engineering. None require the LLM. All are grounded in the durable-reality substrate the seed corpus is currently building.

This list is operator-authored, not exhaustive. Once the corpus lands and we can actually see the reward field, more capabilities will surface. The point is: pass/fail prediction is the **floor**, not the ceiling.

---

## 1. Failure-shape fingerprints

**Claim:** Patches that look unrelated *lexically* may share **failure geometry** across embedders.

**Mechanism:** When E1 (semantic) says two chunks are far apart but E7 (code) + E_DataFlow + E_TypeGraph all cluster them together in an embedding subspace that historically failed oracle, that subspace is a **failure-shape fingerprint**. Examples:
- Bad API assumptions (call signature mismatch, wrong return type expected)
- Stale import paths (module renamed, import not updated)
- Type contract mismatch (None reaches non-Optional, dict reaches list-typed param)
- Missing branch coverage (added a code path with no test)
- State mutation in the wrong layer (mutating shared state from a function that shouldn't)
- Exception swallowing (`except: pass`)
- Bad boundary handling (missing `if` for empty/zero/null edge case)

**Output:** ME-JEPA learns *"this patch shape tends to fail reality even before tests run"* and surfaces the fingerprint name + the nearest historical exemplar.

**Status:** Reachable from current corpus + 12 embedders + frozen E_DataFlow / E_TypeGraph instruments once Phase G trains them.

---

## 2. Claim-to-disk existence prediction (Q1, deeper)

**Claim:** For agent claims like *"I added validation to X"*, the system can predict whether the claimed behavior **actually exists in the bytes** vs the edit only touching adjacent surface area.

**Mechanism:** Compare the structured-claim atomic assertion `(verb=added, target=validation, location=X)` against:
- AST diff (typed structural delta in `X`)
- File-level witness chain (did `X`'s SHA change?)
- Context embeddings of `X` pre-edit and post-edit
- Reachability: is the claimed behavior in the new control flow?

**Output:** Per-claim verification status (verified / refuted / adjacent) with reasoning.

**Status:** Q1 head, design done, implementation Phase G+. The structured-claim parser is the open work.

---

## 3. Oracle outcome prediction before execution

**Claim:** With SWE-bench labels + generated mutation outcomes, the predictor maps `(before code, patch, context)` to the **frozen-instrument target panel**: test pass/fail, parse health, import health, call-graph deltas, dependency touch points, warning profiles, affected symbols.

**Mechanism:** This is the **core Q2 head**, calibrated against `E_Oracle`. The Phase G training run is exactly this objective. ME-JEPA emits a calibrated probability of oracle Pass with a conformal interval.

**Output:** `Verdict::Pass | Fail | OutOfDistribution | Abstain | GuardRejected` + per-test predicted outcomes + per-instrument predicted deltas.

**Status:** Currently 0.867 oracle correlation; gating on Phase G to reach 0.95.

---

## 4. Hidden reward from embedder disagreement

**Claim:** The strongest signal may be when **embedders disagree**.

**Mechanism:** For each chunk, compute disagreement across the 66 unordered embedder pairs:
- E1 (semantic) says "high similarity to centroid"
- E8 (graph) says "structurally distant"
- E6 (sparse) sees "API token drift"
- E2/E3/E4 (temporal) sees "pattern emerged after a dependency-era boundary"

When the embedders disagree on a chunk's cell membership, the disagreement vector becomes a **high-latent-risk signal**: *"This patch looks semantically similar to passing patches but structurally is different in ways our other embedders catch."*

**Output:** Per-chunk disagreement score; surfaced as `Verdict::Abstain` triggers or as an explicit `embedder_disagreement_severity` field in `RealityPrediction`.

**Status:** Reachable directly from the forward-cache once cells materialize. The 66 pairwise cosines are part of the 155-signals-per-chunk reward field.

---

## 5. Repository-specific invariants

**Claim:** The corpus can reveal **project-level laws** that don't generalize across projects but are sharp within a project:
- Which files tend to co-change (the "this PR usually touches both `models/` and `migrations/`" pattern)
- Which call paths are fragile (functions where 80% of past edits broke the test suite)
- Which test files validate which source paths (`tests/test_X.py` is the ground truth for `src/X.py`)
- Which AST shapes correlate with regression (e.g., `try/except` around `requests.get` in django repo correlates with future test flakes)
- Which import/module edges break often (e.g., `from .util import *` is a regression magnet)

**Mechanism:** Per-project cells. The cell key includes `project_id`, so the predictor learns per-project signatures. Cross-project transfer happens via the embedders' pretrained semantic component.

**Output:** Per-project invariant index; surfaced in Q5 (Reality Impact) as "this patch violates a learned invariant of repo X."

**Status:** Reachable after Phase G corpus training. Per-project cell stratification is already in the design.

---

## 6. Patch blast-radius prediction

**Claim:** Multi-embedder correlations can answer **"what else could go wrong?"** by identifying chunks whose embeddings shift in relation to the patch even though they weren't edited. Surfaces hidden affected areas: tests, dependency callers, config paths, serialization contracts, performance-sensitive loops, security boundaries.

**Mechanism:** For each chunk in the codebase (not just the patched chunks):
1. Compute its post-edit joint embedding (counterfactual: how would this chunk's vectors change if the patch's typed-delta propagated to it?)
2. Compare to pre-edit embedding.
3. Rank by shift magnitude.
4. Surface top-K affected chunks as blast radius.

**Output:** Per-patch ranked list of affected chunks, each tagged with affected dimension (test / config / serialization / perf / security).

**Status:** Q5 head head; reachable after Phase G + static-reality-graph integration.

---

## 7. Counterfactual repair ranking

**Claim:** Once the target instruments are stable, ME-JEPA can **score candidate fixes before execution**: *"this edit is more likely to satisfy the oracle and preserve invariants than that edit."*

**Mechanism:** The agent emits N candidate patches. For each:
1. Run the full 12-embedder forward.
2. Materialize the predicted post-edit panel.
3. Run the predictor head → get `(predicted_oracle_pass, confidence, OOD_score)`.
4. Rank the N candidates by `predicted_oracle_pass × (1 - OOD_score)`.
5. Return the ranking to the agent or operator.

This becomes **feedback to coding agents without relying on the LLM's self-assessment**.

**Output:** Per-candidate-patch score; the agent picks the top-ranked patch to apply.

**Status:** Already partially exposed via `mejepa_predict_what_if` MCP tool. Full counterfactual ranking is post-ship-gate work.

---

## 8. Calibration of uncertainty

**Claim:** The system can **learn when it does not know**.

**Mechanism:** Out-of-distribution detection. If:
- The joint embedding falls in a low-density region of the training distribution
- Cell membership is weak (no centroid within Gτ threshold)
- Historical patches with similar fingerprints split between Pass and Fail (high entropy)
- Conformal interval too wide

Then ME-JEPA emits `Verdict::Abstain` + a `missing_evidence` field describing what specifically is unprecedented about this patch.

**Output:** Honest "I don't know" verdict with structured reasoning about why, instead of overclaiming.

**Status:** Conformal calibration + OOD score are part of the Q2 head. Phase G includes per-cell OOD AUC ≥ 0.90 as an auxiliary gate.

---

## 9. Teleological constellations (intent-linked chains)

**Claim:** Define these as the full chain:

```
operator goal
   → agent claim
      → edit event
         → AST delta
            → embedded chunk constellation
               → frozen instruments
                  → oracle outcome
                     → feedback
```

The reward signal is not just pass/fail; it is the **entire observed chain** of whether the edit moved durable reality toward the intended purpose.

**Mechanism:** Per-chunk, per-edit-event traversal of the chain. Each arrow is a deterministic transformation. The predictor learns the joint distribution over the chain, not just the marginal P(oracle_pass | chunk).

**Output:** Q5 head's `goal_alignment` score; the chain itself surfaced in `mejepa_explain_prediction`.

**Status:** Core to the architecture; fully realized after Phase G + operator-goal embedding from session UserPromptSubmit events.

---

## 10. Review-replacement primitives

**Claim:** Not *"replace human review"* immediately, but build the primitives that make review **statistically reducible**:
- Existence verification (Q1)
- Work prediction (Q2)
- Failure-reason prediction (Q3)
- Edge-risk prediction (Q4)
- Impact prediction (Q5)
- Confidence calibration tied to observed oracle outcomes

**Mechanism:** Each primitive is its own head; together they cover what a senior engineer mentally checks during code review.

**Output:** When all five primitives are calibrated above their per-cell thresholds, **review becomes statistically reducible**: the operator only reads the patches where one or more primitives are uncertain.

**Status:** This is the design goal. The 0.95 ship-gate is the operational definition.

---

## Beyond the user's list — what else the corpus enables

### 11. Reverse-direction prediction (why did the agent emit this patch?)

The same predictor that predicts oracle outcome from patch can be inverted to predict patch from goal. Useful for:
- Operator-side "what would ME-JEPA suggest as a fix?" tool
- Agent self-critique: agent emits patch, calls `mejepa_predict_what_if` for a counterfactual patch, compares
- Adversarial generation: produce patches that the predictor thinks will pass but reality says fail (active-learning data)

### 12. Per-agent fingerprinting

The corpus + live data builds a profile per AI agent: *"Claude Code's `subtle_flip` rate is 2%, Cursor's is 5%, Aider's is 1%."* Operators can pick agents per task. Agents can be measured for honesty (rate of fluent-but-refuted claims).

### 13. Drift detection across model versions

When the LLM upgrades (e.g., Claude 4.7 → Claude 5.0), the agent's distribution of patches shifts. ME-JEPA's drift detector catches it: cells whose recent live predictions diverge from historical baseline get flagged. This is the operator's signal that the upstream model changed behavior.

### 14. Code-specific embedding training

Right now the embedders are frozen pretrained. The corpus is large enough (~4.9 M vectors) that selective fine-tuning of specific embedders on the failure-mode contrastive pairs is feasible. Not in scope for Phase G, but plausible post-ship.

### 15. Per-language transfer learning

Once Python ships, the cross-lingual embedders (E14 BGE-M3 especially) carry signal to Rust, TypeScript, etc. The per-language ship gate need not re-run from scratch; it inherits Python's reward field where applicable.

### 16. Active counterfactual search

Given a `Verdict::Fail` patch, search the embedding neighborhood for the nearest `Verdict::Pass` patch. Emit it as a suggested fix. This is "auto-repair" without the LLM. Bounded by: the suggested patch must come from the corpus, not be hallucinated.

### 17. Repository-specific Gτ thresholds

The Gτ guard threshold is per-cell. Some repos (django, sympy) have high intra-cell variance because they touch a broad surface area; their Gτ is permissive. Others (a small library with tight invariants) have low intra-cell variance; their Gτ is strict. The system can learn the right per-repo permissiveness.

### 18. Operator-attention scoring

Track which patches the operator override versus which they leave alone. Train a meta-model that predicts operator attention. The agent can then ask: *"is the operator likely to override this prediction?"* and react accordingly (rebase, ask for clarification, raise confidence threshold).

### 19. Goal drift detection

The operator's stated goal at the start of a session (extracted from UserPromptSubmit events) defines a reward direction. As the session progresses, ME-JEPA tracks whether the agent's edits are moving toward or away from that direction. Goal drift becomes a Q5 sub-head.

### 20. Cost / latency / VRAM regression prediction

Each embedder's forward time is measured. Each instrument's computation cost is measured. Patches that increase predicted runtime cost across the pipeline get flagged in Q4's `cost_regression` sub-head. Not theoretical — the telemetry data already exists; just needs to be wired into a prediction head.

---

## The unifying principle

**Embeddings alone will not prove reality.** The labels and frozen instruments are what keep the system grounded. The multi-embedder layer gives ME-JEPA richer predictive coordinates; the durable-reality instruments supply the target truth that prevents collapse and prevents the model from learning vibes.

Each future capability above is one of two things:
1. A new head on top of the existing 12-embedder × 15-instrument substrate (cheap to add once substrate is built)
2. An expansion of the corpus or instrument set (slower; new FSV evidence required)

Both classes are tractable. The system is genuinely *built to be extended*: the architecture admits new heads without re-training the predictor backbone, and admits new instruments without breaking the collapse-immunity proof (as long as the new instruments are frozen, deterministic, and registered in the panel slot enum).

---

## What we'll know once the corpus lands

We're speculating right now because we can't see the reward field yet. Once the forward-cache run finishes on aiwonder (~20 hours from now), we will be able to see:

1. **Empirical embedder agreement / disagreement distributions per cell.** This will tell us which capabilities above are immediately reachable vs which need more data.
2. **Actual per-cell variance.** Some cells will be tight; some will be sprawling. Tight cells are easy; sprawling cells may need sub-division.
3. **Real Gτ threshold values per cell.** Calibration not theory.
4. **The 462-or-155 signal density per chunk.** We've been estimating; we'll measure.
5. **Which embedders dominate which cells.** Routing strategy.
6. **The OOD distribution.** What does "out of distribution" actually look like for code embeddings on this corpus?

Most of these capabilities are *consequences* of building the corpus. The corpus is what produces the answers, not the speculation.

---

## TL;DR

Pass/fail prediction is the floor. With the substrate the corpus produces, the system can also predict: failure shapes, claim-existence, blast radius, repository invariants, counterfactual repairs, operator attention, goal drift, and a dozen other capabilities. Most are cheap once the substrate exists. The substrate is being built right now.

# 13 — Glossary

Every term defined once. Alphabetical.

---

**Active learning queue** — `CF_MEJEPA_ACTIVE_LEARNING_QUEUE`. Chunks the daemon has flagged for operator review because they hit OOD thresholds, blind-spot z-scores, or low-density cells. Drainable via `mejepa active-learning list|label|dismiss` CLI.

**Adversarial corpus** — 30 hand-authored Python patches that exercise specific failure modes (`SubtleBugPassesTests`, `KnownGoodLookalike`, `EmbedderGaming`). Binds into the ship gate; predictor must classify ≥ 24/30 with `pass_at_high_confidence == 0`.

**Asymmetric embedder** — An embedder that produces different vectors depending on whether the input is "cause" vs "effect", "source" vs "target", or "document" vs "query". E5 (causal), E8 (graph), E10 (paraphrase) are asymmetric.

**Blast radius** — The set of files/symbols/tests/configs that a patch is predicted to affect, even if the patch doesn't directly edit them. Output of Q5 head.

**Blind spot** — A chunk where one embedder's view of the cell membership disagrees with another's by more than a calibrated z-score threshold. Blind spots get pulled into active learning at high priority.

**CBP (Continual Backprop)** — Plasticity-preservation technique for online retrain. Tracks per-unit utility; re-initializes low-utility units. Prevents the predictor's MLP from "dying" over months of training.

**Cell** — A row of `CF_MEJEPA_TCT_CELLS`. A group of chunks sharing the same teleological constellation key (typically `mutation_category × language × project`). Holds centroid, variance, oracle outcome distribution, Gτ threshold.

**Cell stratification** — The convergence requirement that *every cell* hits `prediction_oracle_correlation ≥ 0.95`, not just the aggregate. Prevents shipping on high overall correlation hiding poor adversarial-cell performance.

**CF (Column Family)** — RocksDB partition. ME-JEPA uses 51+ CFs (`CF_MEJEPA_PANELS`, `CF_MEJEPA_LIVE_PREDICTIONS`, `CF_MEJEPA_TCT_CELLS`, etc.).

**Chunk** — An AST-aware unit of code (function, class, import, test block, fixture). Decomposition from `python_ast_chunks.py`. The atomic unit the embedders see.

**Claim** — Natural-language assertion the AI agent makes about its edit (e.g., *"I added input validation to parse_user_input"*). Parsed into atomic `(verb, target, qualifier)` tuples for Q1 reconciliation.

**Conformal calibration** — Statistical procedure that converts raw predictor scores to calibrated probabilities with coverage guarantees. Per-cell residual distribution fit on a held-out calibration set.

**Constellation** — See **Teleological constellation**.

**`context-graph-mejepa-*` crates** — The Rust crates that implement the system. Each is independently testable and FSV-verified.

**Corpus** — The training data. Currently: 300-task SWE-bench Lite × 8 mutation categories = 2,400 (instance, mutation) cells → 399,777 AST chunks → ~4.9 M (chunk, embedder) records.

**Daemon** — The continuous self-optimization process. Tails the shift log, materializes panels, ingests operator feedback, retrains predictor, recalibrates conformal, evicts drifting cells.

**DDA (Data-Driven Augmentation)** — Per-chunk reward signals computed from embedder agreement: cosines to centroid, pairwise cosines, pairwise MIs, blind-spot z-scores. Persisted to `CF_MEJEPA_DDA_SIGNALS`.

**Docker oracle** — The official SWE-bench evaluator container per task instance. Runs the test suite and exit-codes with FAIL_TO_PASS / PASS_TO_PASS / FAIL_TO_FAIL / PASS_TO_FAIL sets. Deterministic ground truth for the `E_Oracle` instrument.

**Drift detector** — Bayesian small-window detector that fires when a cell's oracle outcome distribution or its embedding distribution shifts significantly. Triggers emergency eviction + retraining.

**EWC (Elastic Weight Consolidation)** — Catastrophic-forgetting protection. Per-parameter Fisher information tracked online; high-Fisher parameters get strong penalty against updates.

**E1, E2, ..., E14** — The embedder slot identifiers. See [`06_EMBEDDER_STACK.md`](06_EMBEDDER_STACK.md) for the full list.

**E_Oracle, E_AST, E_DataFlow, etc.** — Frozen instrument slot names. 15 total. See [`05_FROZEN_INSTRUMENT_PANEL.md`](05_FROZEN_INSTRUMENT_PANEL.md).

**Embedder** — A function from `text → Vec<f32>` (or `text → Vec<Vec<f32>>` for late-interaction). 12 active content embedders in the current Python forward-cache run.

**Embedder slot** — A registered (id, dim) pair in the `EmbedderId` enum. Asymmetric embedders consume two slots.

**Existence prediction** — Q1 head's job. Does the bytes-on-disk delta match the agent's natural-language claim?

**ext4 journal** — The Linux journaling filesystem on the OS root disk. `jbd2_log_wait_commit` is the kernel state when a process is waiting for an ext4 journal commit. Observed as a bottleneck when the hot stage is on ext4 instead of ZFS.

**Fail-closed** — Design principle: when a check fails or input is invalid, refuse the operation with a structured error code rather than guess or proceed. Used throughout: `MEJEPA_PANEL_DIM_MISMATCH`, `REDACTION_NONUTF8`, etc.

**Forward-cache run** — The job that produces per-chunk per-embedder vector records across the corpus. Currently grinding on aiwonder.

**Frozen instrument** — A deterministic function with no trainable parameters that produces part of the target panel. Why ME-JEPA can't collapse.

**FSV (Forensic Source-Verified)** — Project verification protocol. Every primitive emits structured evidence (`before / after / readback`) to `/mnt/d/contextgraph/fsv/<task>-fsv/` or `/zfs/archive/contextgraph/fsv/...`. The truth contract for "is this implemented correctly?"

**Gold patch** — The actual fix in the SWE-bench Lite task. Should produce `OracleVerdict::Pass` on the Docker oracle. The `known_good` mutation category is identity-on-gold-patch.

**Gτ guard** (gamma-tau guard) — Per-cell threshold on chunk-to-centroid distance. If a chunk's distance exceeds Gτ, the predictor emits `Verdict::GuardRejected`. The cell-membership-conflict check.

**Hot root** — The fast-disk staging area for in-progress shard work. Currently on `/home/croyse/.cache/contextgraph/...` (ext4 OS root). Future optimization: move to ZFS hot pool.

**Instrument** — See **Frozen instrument**.

**Isolated embedder processes** — The `--isolate-embedder-processes` Rust runner flag that spawns one cargo subprocess per embedder per shard. Enables par=6 GPU concurrency on a single 32 GB RTX 5090.

**JEPA (Joint-Embedding Predictive Architecture)** — Class of architectures where a predictor maps input → some representation that matches a target representation produced from a related input. ME-JEPA-Code's innovation: the target representation has zero trainable parameters.

**LLM (Large Language Model)** — Not part of ME-JEPA. The untrusted edit generator. ME-JEPA verifies the LLM's output without consulting the LLM.

**MCP (Model Context Protocol)** — JSON-RPC stdio protocol for AI agent ↔ tool communication. ME-JEPA serves 28 `mejepa_*` tools over MCP.

**Mutation category** — One of 8 deterministic code mutations applied to gold patches: `known_good`, `subtle_flip`, `off_by_one`, `swap_variable`, `delete_test_call`, `wrong_file`, `over_engineer`, `compile_error`.

**Online retrain** — The daemon's continuous training cycle that ingests live predictions, operator feedback, and shift log events.

**OOD (Out of Distribution)** — Verdict emitted when the joint embedding falls outside the training distribution. Predictor refuses to commit to Pass/Fail.

**Operator** — The human running the system. Not the AI agent. Has authority to override predictions (`mejepa_record_agent_feedback`), approve promotions (`mejepa_promote_approval`), and edit forbidden paths.

**Operator override** — `mejepa_record_agent_feedback` invocation. Pulled into replay buffer at 6× weight.

**Panel** — The 5,120-d target representation produced by the 15 frozen instruments for a given (chunk, edit) event. Stored in `CF_MEJEPA_PANELS`.

**par (parallel)** — The `CG_MEJEPA_PY_FORWARD_PARALLEL_EMBEDDERS` env var. Number of cargo subprocesses run concurrently per shard. par=6 stable; par=12 OOMs.

**Pearson correlation** — The statistic the ship gate measures. ρ ≥ 0.95 per cell.

**Phase G** — The current convergence phase. Targets the 0.95 oracle correlation gate. Item-by-item plan in `docs/futurebuild/27_PHASE_G_ROADMAP.md`.

**Prediction ID** — `Vec<u8; 16>` (32 hex chars). Unique key per emitted `RealityPrediction`. Used in `mejepa_record_agent_feedback` to link feedback to prediction.

**Predictor** — The trained MLP head. Maps (joint embedding, panel_t1) to (predicted panel_t2). The only part of the system that has trainable parameters.

**Q1, Q2, Q3, Q4, Q5** — The five operator questions: EXIST, WORK, WHY, WHAT ELSE, IMPACT. See [`04_FIVE_OPERATOR_QUESTIONS.md`](04_FIVE_OPERATOR_QUESTIONS.md).

**Quantization tiers** — 8/7/5/3-bit per-vector linear scalar quantization. Hot/warm/cold/archive storage. Cosine retention 0.99999 / 0.99997 / 0.99960 / 0.99192 on 768-d Gaussian.

**Reality compiler** — The (planned) per-project full-rerun of the chunker + embedder + instrument pipeline against a customer's repo. Materializes the per-project cells + per-project Merkle cache. Foundation for repository-specific invariant learning.

**Reality-shift principle** — *"No alteration without current state. No alteration without a delta back into perception."* Pre/post-tool hooks enforce this.

**RealityPrediction** — The structured output of a prediction call. Contains Q1-Q5 fields + verdict + confidence + conformal interval + nearest exemplars + violating embedders.

**Replay buffer** — `CF_MEJEPA_REPLAY_BUFFER`. Prioritized sampling buffer for the daemon's online retrain. Operator overrides at 6× weight.

**Routing** — Per-cell weight profile lookup. `mejepa_routing_lookup` returns which embedders' opinions count most for a given cell.

**Shard** — A chunk of 1024 chunks the forward-cache run processes as a unit. 391 shards in the seed corpus.

**Ship gate** — `prediction_oracle_correlation ≥ 0.95 × 4 windows × per cell`. The single convergence metric.

**Shift log** — Append-only JSONL of typed reality events (Edit, Write, test outcomes, prediction emissions). Tailed by the shift subscriber.

**Shift subscriber** — Tokio task in `context-graph-mejepa-shift-subscriber` that tails the shift log and materializes panels.

**SoT (Source of Truth)** — The durable bytes on disk. The thing FSV evidence reads back from. Never a return value, never an LLM's claim. The `/zfs/archive/contextgraph/` paths on aiwonder, the RocksDB row, the JSONL row.

**SWE-bench Lite** — The 300-task Python benchmark from Princeton NLP. `princeton-nlp/SWE-bench_Lite` on HuggingFace.

**Target representation** — `f_target(panel_t2)`. The 5,120-d output of the frozen instruments. The predictor's training objective.

**TCT (Teleological Constellation)** — The intent-linked chain from operator goal → oracle outcome. Cell key includes mutation category, language, project.

**Teleological constellation** — See TCT.

**True batch** — The actual GPU forward batch size, distinct from the per-embedder batch size. `--true-batch-size 8` means each GPU call processes 8 chunks.

**UTML (Unified Training Markup Language)** — Per-cell parameter carrier system for loss weights, Fisher info, dormancy scores, dissipation thresholds. Implementation: TASK-UTML-005..008.

**Verdict** — The Q2 head's output: `Pass | Fail | OutOfDistribution | Abstain | GuardRejected`.

**Witness chain** — Merkle-rooted hash chain of chunk contents + parent commits. The `E_Witness` instrument's input. Implementation in `context-graph-witness` crate.

**ZFS** — The Zettabyte File System. aiwonder uses ZFS for the hot pool (1.8 TB NVMe) and archive pool (9.0 TB HDD mirror). Mount points: `/hotpool` and `/archive`. `/zfs/hot/contextgraph/` and `/zfs/archive/contextgraph/` are the project's working / durable roots.

# 14 — Failure-Shape Fingerprints: The First-Class ME-JEPA Object

**Status:** Canonical methodology document. Supersedes the looser "cell" language in `07_TELEOLOGICAL_CONSTELLATIONS.md`.

**Relation to PAPER.md:** This doc is the direct application of Chris Royse's *Teleological Constellation Training* (TCT) protocol (PAPER.md §§3–5) to the code-verification problem. The constellation $C_P$ that PAPER.md uses for identity-locked generation is the same mathematical object ME-JEPA uses for failure-mode classification, with a different referent: instead of "the geometric definition of person P," it's **"the geometric definition of failure-shape fingerprint F."** The three-role composition (retriever / labeller / runtime guard) over the same 12 frozen embedders transfers without modification.

---

## 0. The thesis in one paragraph

ME-JEPA-Code stores and trains against a **catalog of failure-shape fingerprints**. Each fingerprint is a frozen multi-embedder centroid set $C_F$ that encodes "this is what a patch of failure mode $F$ looks like across all 12 embedders simultaneously." The catalog has three typed entries: **KnownGood** (Pass-shaped — the gold-patch geometry), **KnownBad** (Fail-shaped — one per documented failure mode), and **Unknown** (out-of-distribution — patches that match no known fingerprint, queued for operator labeling). The verifier's job for a new patch is to (1) compute its 12-embedder joint embedding, (2) score it against every fingerprint in the catalog via the $G_\tau$ guard, (3) emit the typed verdict (Pass / Fail-with-fingerprint-name / Unknown), and (4) when Unknown, route to active learning so the catalog grows. The system gets better at edge cases the more it encounters them.

## 1. The fingerprint object, formally

**What's actually running on aiwonder right now** (verified against shard 0 packed_records 2026-05-15T23:30Z):

| Tier | Count | Slots | Role |
|---|---|---|---|
| Neural GPU embedders (the heavy lifters) | **8** | E1, E6, E7, E8, E10, E12, E13, E14 | Carry the discriminative signal — what fingerprints actually separate on |
| Algorithmic CPU embedders (free accompaniments) | 4 | E2, E3, E4, E9 | Cheap positional / cyclic / hyperdimensional encodings; cost no GPU |
| **Forward-cache total** | **12** | — | All 12 produce packed_records per chunk |

**The fingerprint catalog is built from the 8 neural embedders.** The 4 algorithmic ones supplement at near-zero cost and may participate in specific fingerprint definitions (especially for temporal / cyclic failure patterns), but the heavy discriminative signal lives in the 8 neural slots. Per-fingerprint weight profiles ([`06_EMBEDDER_STACK.md`](06_EMBEDDER_STACK.md) §"Layer 3") can further downselect: some fingerprints may calibrate sharply against E7 (Qodo code) + E1 (semantic) + E_DataFlow only, weighting the others at zero.

Let $D$ be the chunk corpus. Let $\Phi_{\text{neural}} = \{\phi_e\}_{e \in \{1,6,7,8,10,12,13,14\}}$ be the 8 frozen **neural** content embedders that carry the discriminative signal. Let $\Phi_{\text{algorithmic}} = \{\phi_e\}_{e \in \{2,3,4,9\}}$ be the 4 algorithmic embedders that supplement. A **failure-shape fingerprint** is:

```rust
pub struct FailureShapeFingerprint {
    /// Stable identifier. SHA-256 of the canonical key tuple.
    pub fingerprint_id: FingerprintId,

    /// Typed kind — answers "what does this fingerprint mean?"
    pub kind: FingerprintKind,

    /// Human-readable name. Required.
    pub name: String,                            // e.g. "subtle_flip_comparison_operator"

    /// Frozen per-embedder centroid set (PAPER.md §5.1 C_P, applied to failure modes).
    pub centroid_per_embedder: HashMap<EmbedderId, Vec<f32>>,   // 12 vectors

    /// Per-embedder variance — used for confidence calibration.
    pub variance_per_embedder: HashMap<EmbedderId, f32>,

    /// Per-embedder Gτ acceptance threshold (PAPER.md §5.4).
    pub tau_per_embedder: HashMap<EmbedderId, f32>,

    /// Aggregate-pair information: cosine + MI for the 66 pairs.
    /// Captures cross-embedder fingerprint geometry.
    pub pairwise_cosine: HashMap<(EmbedderId, EmbedderId), f32>,
    pub pairwise_mi: HashMap<(EmbedderId, EmbedderId), f32>,

    /// Reference chunks that constitute the fingerprint's geometric definition.
    pub reference_chunks: Vec<ChunkId>,
    pub n_references: usize,

    /// Oracle outcome (deterministic for KnownGood/KnownBad; absent for Unknown).
    pub oracle_outcome: Option<OracleOutcome>,
    pub exception_class: Option<ExceptionClass>,

    /// Provenance.
    pub created_at: Timestamp,
    pub last_refreshed: Timestamp,
    pub source_corpus: CorpusVersion,

    /// Active-learning state.
    pub is_canonical: bool,                      // operator-confirmed?
    pub confidence: FingerprintConfidence,       // calibrated by holdout performance
}

pub enum FingerprintKind {
    /// Patches that pass the Docker oracle. The "gold-patch geometry."
    KnownGood {
        gold_patch_variants: usize,              // count from corpus
    },

    /// Patches that fail the Docker oracle in a specific named way.
    KnownBad {
        mutation_category: MutationCategory,     // subtle_flip | off_by_one | ...
        failure_mode_description: String,        // human-readable
        nearest_oracle_exception: ExceptionClass, // TypeError | AssertionError | ...
    },

    /// Out-of-distribution. Doesn't match any known fingerprint.
    /// Lives in this state until operator labels it.
    Unknown {
        observed_at: Timestamp,
        observed_by_session: SessionId,
        ood_score: f32,
        embedder_disagreement_score: f32,
        active_learning_priority: u8,            // 1=high, 5=low
    },
}
```

Persisted to RocksDB CF `CF_MEJEPA_FAILURE_FINGERPRINTS`, keyed by `fingerprint_id`.

## 3. The verification flow (replacing per-cell correlation)

When a new patch arrives, the predictor:

```
1. Compute 12-embedder joint embedding of the patch's chunks.

2. Score against the entire fingerprint catalog:
   for each F in catalog:
       g_τ(F) = ∀ e ∈ active_embedders: cos(φ_e(patch), F.centroid_per_embedder[e]) ≥ F.tau_per_embedder[e]
       if g_τ(F) holds:
           matched.append(F, similarity_score=mean_cosine_to_F)

3. Apply typed decision logic:
   if any matched F has kind=KnownGood and no KnownBad matched:
       emit Verdict::Pass
       attach: best_matching_good_fingerprint
   else if any KnownBad matched:
       emit Verdict::Fail
       attach: nearest_failure_fingerprint, predicted_exception_class, top-3 ranked
   else if all g_τ failed (no fingerprint matches):
       emit Verdict::OutOfDistribution
       enqueue chunk to CF_MEJEPA_ACTIVE_LEARNING_QUEUE with Unknown fingerprint placeholder
       priority = f(ood_score, embedder_disagreement_score)
   else:
       emit Verdict::Abstain (mixed signals, no clear winner)
```

This is **fingerprint classification**, not real-valued regression against oracle probability. The output is structurally explainable: *"this patch matches fingerprint `subtle_flip_django_comparison_operator` with mean cosine 0.94 across 12 embedders; the nearest historical exemplar is `django__django-12286#subtle_flip`."*

## 4. Edge-case capability (the new-fingerprint loop)

ME-JEPA must handle patches it has never seen before. When the typed decision logic emits `Verdict::OutOfDistribution`, the system does **NOT** fail — it activates the lifelong-learning loop:

```
1. Patch goes to CF_MEJEPA_ACTIVE_LEARNING_QUEUE.
2. The chunk's 12-embedder joint embedding is preserved.
3. The chunk's actual oracle outcome (once observed, via test run or operator override) becomes the label.
4. If multiple unlabeled chunks cluster in the same OOD region (≥ K with cosine similarity ≥ τ_cluster):
     a. The cluster becomes a candidate new fingerprint.
     b. Operator is notified via `mejepa active-learning suggest-new-fingerprint`.
     c. Operator labels: confirms kind (KnownGood/KnownBad), assigns name + exception class.
     d. New fingerprint is added to catalog, persisted to CF_MEJEPA_FAILURE_FINGERPRINTS.
     e. Next training cycle pulls the new fingerprint into the replay buffer at 6× weight.
5. The catalog grows monotonically. The system never forgets a fingerprint (EWC protection).
```

This is the **"optimized for edge case learning"** property. The catalog at seed is 97 fingerprints. After six months of live use, it might be 500. After a year, 1,000. Each new fingerprint encodes a failure mode the operator's codebase actually produces, not a hypothetical one the corpus designers thought of in advance.

**Active-learning priority levels:**

| Priority | When assigned | Behavior |
|---|---|---|
| **1 — critical** | Cluster of ≥ 10 OOD patches with similar geometry | Operator alerted immediately; blocks corpus retrain until resolved |
| **2 — high** | OOD patch with embedder disagreement > 2σ | Surfaces in `mejepa active-learning list` first |
| **3 — medium** | Single OOD patch | Joins queue tail |
| **4 — low** | OOD patch with near-match to existing fingerprint | Suggested re-classification of existing fingerprint |
| **5 — defer** | OOD patch on a deprecated cell | Archive without alerting |

## 5. The good-vs-bad asymmetry

Verification has a structural asymmetry the original TCT didn't need:

| | KnownGood | KnownBad |
|---|---|---|
| **Per fingerprint, what does $G_\tau$ match mean?** | "This patch looks like a known-passing patch" | "This patch looks like a known-failing patch" |
| **What's the verdict on match?** | `Verdict::Pass` (with caveats from Q4) | `Verdict::Fail` (with predicted exception class) |
| **What's the verdict on non-match?** | Possibly Pass via Q4 silence; possibly OOD | Not Fail; need positive match elsewhere |
| **How is the centroid built?** | L2-normalized mean of `known_good` cell members | L2-normalized mean of `mutation_category=X` cell members |
| **How is $\tau$ calibrated?** | Same-session-band floor (10th percentile of `known_good` calibration set) | 10th percentile of mutation-category calibration set |
| **What happens at saturation?** | Cell auto-subdivides by repo, AST node type, framework | Cell auto-subdivides by specific exception class, failure location |
| **Operator override behavior** | Promote a chunk to canonical KnownGood reference | Mark a chunk as canonical KnownBad reference, set its exception class |

The verifier must check **both** sides of the catalog before emitting Pass. A patch can simultaneously match `KnownGood:django_simple_function` AND `KnownBad:subtle_flip_django_comparison_operator` — that's the **conflict** case, which emits `Verdict::Abstain` and routes to operator review.

## 6. Calibration: per-fingerprint, not per-cell-correlation

The original ship gate metric (`prediction_oracle_correlation ≥ 0.95 × 4 windows × per cell`) becomes:

```
For every fingerprint F in catalog:
    classification_accuracy(F) ≥ 0.95          // patches that should match F do match F
    classification_precision(F) ≥ 0.95         // patches that match F should match F (no false ID)
    unknown_recall ≥ 0.90                      // patches that are truly OOD are emitted as Unknown
    must be stable across 4 rolling windows
```

This is per-fingerprint, not per-aggregate. It enforces:
1. Every KnownGood fingerprint is correctly identified ≥ 95% of the time it appears.
2. Every KnownBad fingerprint is correctly identified ≥ 95% of the time it appears.
3. False positives across fingerprints stay below 5%.
4. Truly novel patches get emitted as Unknown at ≥ 90% rate (not silently misclassified as a known fingerprint).

The ship gate becomes:

```
For all F in catalog: accuracy(F) ≥ 0.95 AND precision(F) ≥ 0.95
AND unknown_recall ≥ 0.90
AND stable across 4 consecutive rolling windows
```

When a new fingerprint joins the catalog (operator-labeled from active-learning queue), it enters in a "calibrating" state. After K observations, its threshold $\tau$ is calibrated and it joins the gated set.

## 7. The three roles, applied (PAPER.md §3.4 → ME-JEPA)

PAPER.md observes that the same frozen embedder panel $\Phi$ serves three roles simultaneously, over **identical parameter instances**, without any parameter update:

| Role | PAPER.md | ME-JEPA-Code application |
|---|---|---|
| **Retriever** | Context Graph ranks stored content by cosine | `mejepa_routing_lookup` ranks fingerprints in the catalog by similarity to a query patch |
| **Labeller** | DDA produces $n \cdot (N + \binom{N}{2})$ supervisory signals on a fixed corpus | Constellation builder produces 155 reward signals per chunk × 399,777 chunks = ~62 M signals to materialize the fingerprint catalog |
| **Runtime guard** | $G_\tau(\hat y; C_P) = \mathbb{1}[\forall m : \cos(\phi_m(\hat y), c_m) \geq \tau_m]$ for the generated output | $G_\tau(\text{patch}; C_F) = \mathbb{1}[\forall e : \cos(\phi_e(\text{patch}), c_e^F) \geq \tau_e^F]$ for the live patch, executed at MCP `mejepa_predict_what_if` time |

No new infrastructure. Three uses of the same 12 frozen embedders.

## 8. The DDA counting identity, applied

PAPER.md §3.1: $|D'| = n \cdot (N + \binom{N}{2})$ structured signals. For ME-JEPA at $N=12$:

| Term | Count per chunk |
|---|---|
| Per-embedder cosine to each fingerprint's centroid | $|catalog|$ × 12 (one per embedder × catalog size) |
| Pairwise cross-embedder cosine | 66 |
| Pairwise cross-embedder MI | 66 |
| Blind-spot z-scores (primary vs enhancer pairs) | 11 |
| **Total (excluding catalog scaling)** | **155 per chunk** |
| × 399,777 chunks in seed corpus | **~62 M reward signals** |

At catalog size 97: **155 + (97 × 12) = ~1,319 signals per chunk** including catalog scoring. This is the substrate the predictor head trains against.

## 11. Why this is the right methodology

Five reasons this beats per-cell oracle correlation as the central object:

1. **Explainability.** Operator sees "this patch matches fingerprint `subtle_flip_django_comparison_operator` (0.94 confidence) — nearest exemplar `django__django-12286#subtle_flip`." That's a verdict the operator can act on. A real-valued correlation score isn't.

2. **Composability with the typed catalog.** Adding a new failure mode = adding a new fingerprint to the catalog. No retraining of a regression head; just new centroids + new threshold + recalibration.

3. **OOD by construction.** If no fingerprint matches, the verdict is `OutOfDistribution` — not a degraded confidence on the regression. The system says "I don't know," and the active-learning loop fixes that.

4. **Aligns with PAPER.md theoretical framework.** TCT, DDA, meaning compression, three-role composition — all the math transfers. The verifiability property (deterministic $O(M \cdot d_{\max})$ test, no auxiliary learned model) holds.

5. **Lifelong learning.** New fingerprints get added; old fingerprints stay stable (EWC + CBP); the catalog grows with the operator's codebase. The system's exposure to edge cases improves the system, doesn't degrade it.

What changes is what the output looks like: a typed catalog of named failure-shape fingerprints, with a growing OOD frontier, instead of a real-valued correlation score.
