# JavaScript AST Binding Symbol Mismatch

## What Happened

The ME-JEPA AST/parser harness for JavaScript used the generic
`first_identifier_text` fallback for `arrow_function` nodes and did not classify
`function_expression` nodes as function definitions. On real persisted semantic
index output, this made:

- `export const double = (x) => { ... }` persist as function symbol `x` instead
  of `double`.
- `export const plusOne = function(value) { ... }` disappear from the function
  symbol graph entirely.
- Exported assigned functions record `visibility: public` instead of
  `visibility: exported` because the parsed function node text excludes the
  enclosing `export const ...` declaration.

The source of truth was
`/tmp/contextgraph-js-ast-repro-before-out/semantic-index.json`, generated by a
real temp git repo with local TypeScript tooling installed under
`/tmp/contextgraph-js-ast-repro-before/node_modules/.bin/tsc`.

## Resolution

JavaScript semantic extraction and live action attribution now resolve function
identity from the binding site that owns the function expression:
`variable_declarator`, `assignment_expression`, object `pair`, or the named
function node. The nested grammar keyword node under `function_expression` is
not indexed as a second function symbol, so one source binding produces exactly
one persisted function symbol. Export visibility is resolved by walking
ancestors, so assigned exported functions persist as `visibility: exported`.

Parser recovery is also fail-closed with structured diagnostics. Syntax errors
do not produce semantic indexes; compiler/LSP batch checks run first and their
stdout/stderr evidence is retained under the output `.evidence/` directory.

symbol each for `double`, `plusOne`, `run`, `stop`, and `load`; parameter names
`x`, `value`, `input`, `reason`, and `config` were absent from the function
symbol set. Edge cases all failed closed without creating the output semantic
index file.

## Why It Matters

ME-JEPA's `E_AST`, action semantics, reverse-reference count, blast-radius
bucket, and semantic symbol graph depend on the symbol identity being the real
JavaScript binding. Parameter-name substitution silently poisons training data
and live prediction features while still returning `status: ok`.

## Root Cause

JavaScript binding names are not always children of the function node. For
assigned arrows/functions, the name lives on the enclosing `variable_declarator`,
`assignment_expression`, or object `pair`. Tree-sitter's own JavaScript tag query
matches those enclosing structures rather than falling back to the first
identifier inside the function body or parameter list.
